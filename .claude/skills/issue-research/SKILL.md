# 調査 — 調べて判断材料を報告する

コードを変えずに調べ、人間が判断に使える報告を残すまでの手順。GitHub でも Azure DevOps
でも同じ手順で動く。調査は開発ループの段ではなく支援工程で、成果物を先の段へ渡さず、
呼んだ段 (設計など) か依頼者に戻す。

## この工程の入口

入口条件: **決めるために調べることがある** (ループの定義は `dev-loop` スキル)。条件が
違う依頼は該当する工程に渡す。

- 調べた結果を仕様に落として起票したい → `issue-design`
- 受け入れ条件の埋まったチケットを実装したい → `issue-implement`
- 失敗しているビルドの原因を調べたい → 能力層のビルドの調べ方 (Azure DevOps は
  `azure-devops` の「ビルド」)

起点はチャットの依頼でも、調査依頼のチケットでもよい。チケットが起点なら「チケットを
読む」でコメントまで読んでから始める。

## 能力層

基盤ごとに違う操作は、この本文に「チケットにコメントする」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

**チケット**は GitHub の Issue、Azure DevOps の作業アイテム。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 何を決めたいかが曖昧 | 調べる前に依頼者に確かめる | 自分の解釈を報告の冒頭に 1 行で書いて進める |
| 報告の置き場所 | 起点のチケットがあれば「チケットにコメントする」。無ければ会話で返す | 「チケットにコメントする」 |

チケットの状態 (GitHub のラベル、Azure DevOps の `System.State`) は、GitHub Actions の
ワークフローが指示したときだけ動かす。チャットからの実行では触らない。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の上限は次の 2 つ。

- 報告は折りたたみの外を **合計 30 行以内**。調べた量ではなく、決めるために必要な量を書く
- 根拠・比較の詳細・調査の経緯は折りたたみに畳む。折りたたみが使えない置き場所 (能力層の
  「チケットにコメントする」が示す) では、根拠は省き、要るならファイルに書いてその場所を
  1 行で示す

## 手順

### 1. 何を決めるための調査かを特定する

起点のチケットがあれば「チケットを読む」で読む。報告の読み手が次に何を決めるのかを
1 文で言えるまで、依頼を読む。決めたいことが分からないまま調べると、読み手が使えない
報告になる。曖昧なときの扱いは「実行文脈による違い」の表のとおり。

同じ調査が既にチケットに残っていることがある。「チケットを探す」で先に探す。

### 2. 調べる

コードベースの読解を主にする。リポジトリの `CLAUDE.md` / `AGENTS.md` /
`.github/copilot-instructions.md` があれば読み、プロジェクトの文脈を掴んでから読む。

外部の検索や取得は、その実行環境で使えるときだけ使う。ネットワークが社内に閉じている
環境もある。到達できない情報源を前提にした計画を立てない。

### 3. 断定できることと、できないことを分ける

確認した範囲でしか断定しない。「たぶん」で書いた結論は、そのまま意思決定に使われる。

断定できないなら、断定できないことと「何が分かれば決まるか」を書く。それ自体が次の行動に
なる。

### 4. 報告する

次の順で書く。該当しない要素は見出しごと省く。

- **結論** — 3 行以内。断定できないなら、その旨と何が足りないかを書く
- **判断材料** — 選択肢があるときだけ。1 案 1 行で、案・利点・欠点を並べる。最大 4 案。
  表が使える置き場所では `| 案 | 利点 | 欠点 |` の表、使えなければ「案 — 利点 / 欠点」
- **推奨アクション** — 最大 3 件、1 件 1 行。人間が次に取る行動として書く
- **根拠** — 箇所は `path:line` で示す。置き方は出力規約のとおり

実装タスクに落とせそうなら、チケットにする場合のタイトルと受け入れ条件の案を根拠の中に
含める。起票はしない。起票するかどうかは人間が決め、起票するなら設計の工程 (`issue-design`)
で行う。

## やらないこと

- ファイルの作成・編集
- チケットの新規作成、状態の更新 (ワークフローの指示があるときを除く)
- 確認していない影響・利用者像・画面名の記述
