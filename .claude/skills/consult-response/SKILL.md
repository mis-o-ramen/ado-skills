# 設計相談レイヤーの応答規約

上流の設計・方針・スコープについて意見を求められたときの、**返答の形式**を定める。
考える内容を削るのではなく、**このターンで人間が下す判断に不要な情報を後回しにする**ためのもの。

`output-contract` スキルを前提とする。ここに書くのは、設計相談のときだけ追加で効く規則。

## 前提: このターンで人間がすること

設計相談で人間が下す判断は「どの方針で行くか」の1つだけ。
実装方法・使うフィールド・具体的な文言は、方針が確定した**次のターン**の話。
先に出すと、判断材料と実装詳細が同じ密度で並び、飛ばし読みができなくなる。

## 出力フォーマット（この順序を守る）

### 1. 結論（最初に置く。3行以内）

推す方針を最初に書く。前置き・共感・課題の要約から始めない。
賛成/反対の表明が必要なら1語で済ませ、理由は根拠セクションに送る。

### 2. 根拠（5件以内、各1〜2行）

- 主張1つにつき、**最も強い証拠を1つだけ**。補強のための2つ目は書かない
- コード参照は `path:line` と「そこに何があるか」の半行のみ。本文に中身を引用しない
  （`<details>` を持てない場では引用しない、という output-contract の既定どおり）
- 3つ以上の対象を同じ軸で比べるときは表を使ってよい（表のほうが密度が高い）
- 原則・判断基準を立てるときは、箇条書き2〜3項目まで

### 3. 選択肢（3件以内、各1行）

- 実行可能な選択肢を並べ、推奨に **推奨** と印をつける。
  意見を求められている場面なので推奨を出す（選択肢を並べるだけは答えていないのと同じ）。
  仕様・トレードオフを人間が決める場面で推奨を付けないのとは区別する
- 各行は「何をするか + 帰結を1句」。**推奨以外を選んだときに何が起きるか**が読めないと、
  人間は推奨を蹴る判断ができない。理由の本体は根拠セクションで済んでいる
- 選択肢が1つしかないなら、選択肢セクションは省いて結論だけにする

```
- **推奨 A** — 何をするか（帰結を1句）
- B — 何をするか（帰結を1句）
```

## 書かないもの

- 実装方法（使うフィールド名、クラス名、関数の呼び出し順）
- サンプル文言・サンプルコード・UI文言の案
- 「おっしゃるとおり」系の同意表明、課題の再要約
- 「〜も考えられます」で始まる、判断に影響しない補足

これらは**捨てるのではなく保持する**。「aの根拠を詳しく」「実装方針を出して」と言われたら、そのターンで即座に出す。

前置き・「まとめ」・コード引用の禁止は `output-contract` にあるので繰り返さない。

## 必ず書くもの

- **懸念・反対意見を1件1行で**。分量を絞ると同意側に寄りやすいので、異論の枠は明示的に確保する。反対意見がないときは書かなくてよいが、「無い」ことを自分で確認してから省く
- **前提が間違っている可能性があるとき**は、選択肢を出す前に1行で確認する。誤った前提のまま選択肢を出すほうが往復が増える

## 分量の目安

折りたたみの外は **20行以内**（目安 12 行）。他のワークフローの上限と同じ単位で数える。
超えるときは、根拠を削るのではなく**根拠の各行を短くする**か、実装詳細が混ざっていないか疑う。
超過が避けられないと判断した場合は、**結論の直後に**「長くなる理由」を1行書く。
1行目は常に結論であり、この1行を冒頭に置かない。

## このスキルを緩める条件

以下のときは通常の応答に戻す。

- ユーザーが明示的に「詳しく」「実装方針まで」「全部書いて」と求めた
- 方針が確定し、issue本文やPR説明を書く段階に移った
- 判断ではなく理解が目的の質問（「なぜこうなっているのか」「この設計の意図は」）

## 出力前のセルフチェック

返答を出す前に自己点検し、外れていれば直してから出す。

`output-contract` のセルフチェックに加えて:

- [ ] 各主張の証拠は1つに絞られているか（補強の2つ目を書いていないか）
- [ ] 実装方法・サンプル文言が混ざっていないか
- [ ] 選択肢は3件以内で、各1行に「何をするか + 帰結」が入っているか
- [ ] 懸念・反対を書いたか、または無いことを確認したか
- [ ] 削った情報を、次のターンで出せる形で保持しているか
- [ ] 20行を超えたなら、結論の直後に理由を1行書いたか
