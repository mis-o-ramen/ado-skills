# 実装 — チケットを実装する

チケットを読み、実装し、プルリクエスト (PR) を作るまでの手順。GitHub でも
Azure DevOps でも同じ手順で動く。

## この工程の入口

入口条件: **受け入れ条件の埋まったチケットがあり、PR が無い** (ループの定義は
`dev-loop` スキル)。条件が違う依頼は該当する工程に渡す。

- チケットが無い、または受け入れ条件を書き起こすところから → 設計の工程
- PR のレビュー → レビューの工程、レビュー指摘への対応 → 修正の工程

依頼の中の数字だけのファイル名 (`2251.md` など) や裸の数字はチケット番号である
ことがある。「チケットを読む」で引き当ててから始める。

## 能力層

基盤ごとに違う操作は、この本文に「チケットを読む」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

用語も能力層に合わせて読み替える。**チケット**は GitHub の Issue、Azure DevOps の
作業アイテム。**受け入れ条件**は Azure DevOps では型ごとのフィールド (受け入れ基準、
再現手順など) にあり、どのフィールドかは能力層で調べる。

Git の操作 (branch / commit / push / diff) は `git` CLI を使う。

## 実行文脈による違い

手順は同じで、人間の承認の取り方だけが違う。

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 着手の承認 | 依頼そのもの | 人間の `ai:go` 付与 |
| 条件が足りない・テストが通らない | チケットにコメントし、依頼者にも伝えて止まる | チケットにコメントし、ワークフローの指示どおりに止まる |
| PR の作成 | タイトル・本文・ブランチを見せて承認を得てから作る | そのまま作る。マージは人間が行う |

チャットで PR の作成に承認を挟むのは、作成がレビュアーへの通知を伴い、エージェントから
取り消せないため。GitHub Actions で挟まないのは、`ai:go` が着手と一緒に作成まで承認して
おり、作られた PR は人間がマージするまで何も進めないため。

チャットで、この手順の抜け (画面を確かめていない、テストが条件を検証していないなど) を
指摘されたら、どうするかを尋ね返さず、抜けた手順まで戻ってやり直す。手順に書かれたことは
依頼の範囲に入っており、改めて承認を得るものではない。やり直した結果、PR 本文と報告を
直してから、何を実行し何が見えたかを伝える。

チケットの状態 (GitHub のラベル、Azure DevOps の `System.State`) は、GitHub Actions の
ワークフローが指示したときだけ動かす。チャットからの実行では触らない。いつ誰が状態を
動かすかは運用が決める。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の規約は次の 3 つ。

- PR 本文の**見出し**はリポジトリの PR テンプレートが正典 (置き場所は能力層)。
  足さない・改名しない。見出しの構成はテンプレートが決め、各欄に何をどう書くかはこの
  手順が決める。例外は、自動テスト不能の条件か、確認手順を割り振った `画面` の条件が
  あるのに、テンプレートに確認手順の欄 (`確認手順` / `手動確認手順`) が無いときの `確認手順` の 1 つだけ。手順が無ければ、誰もその条件を実行して確かめられない
- PR 本文は折りたたみの外を **合計 25 行以内**。実装量が多くても本文は増やさない。
  ただし「受け入れ条件と検証」の表と「確認手順」はこの上限の外に置く。どちらも
  条件の数だけ要る欄で、削った分は人間が質問して取り戻すことになる
- 変更ファイルを列挙しない。PR の画面が既に表示している

## 手順

### 1. 規約を読む

- リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
  従う
- コードを変更するとき、コミットする成果物 (docs / README / ADR / コードコメント / 型定義)
  を書くときは `artifact-writing` スキルに従う。成果物は現在形で書き、そこに至った経緯は
  PR 本文へ移す。スキルが無ければ、外部に根拠がある値・回避策・順序依存には根拠のコメントを付ける
- ブランチ名とコミットメッセージは `git-conventions` スキルに従う
- ユーザーに見える文言を足す・変える・消すなら `ui-copy` スキルに従う。文言規約の場所は
  上の規約ファイルが指している

### 2. 満たすべき条件を読む

「チケットを読む」で本文とコメントを読む。本文より新しい決定がコメントに残っていることが
ある。「親チケットを読む」で親があれば読む。チケット 1 件には「何を」しか書かれておらず、
「なぜ」は親にある。

読んだ受け入れ条件を、番号付きの一覧 (`AC1`、`AC2`…) に書き出す。この一覧が手順 4 の
割り振りと、手順 8 の表の行になる。

- チケットに書かれた単位 (チェックボックス・箇条書き・番号・改行) で 1 件とする。区切りの
  無い散文なら文ごとに区切る。統合・言い換え・要約をせず、本文は原文のまま写す
- コメントで条件が追加・変更されていれば、その件も一覧に入れ、出典のコメントの日付を添える
- 実装の都合で生まれた項目 (ビルドが通る、既存のテストが通るなど) は条件ではないので
  入れない
- 利用者が画面で操作するか、画面に見えることで判定する条件 (「選択すると」「押すと」
  「遷移する」「表示される」など) に `画面` の印を付ける。印は条件の文言だけで決め、
  変更したファイルが画面側かサーバ側かでは決めない。印の付いた条件は手順 4・6・8 で
  画面の確認が要る

一覧はリポジトリの外 (一時ディレクトリ) にファイルとして書き出し、手順 4 と手順 8 は
そこから作る。実装を挟むうちに、条件の記憶は作った物の記憶に置き換わっていく。

### 3. 条件が足りなければ止まる

受け入れ条件が空、または実装が一意に決まらないなら、推測で実装しない。不足している
条件を 1 件 1 行 (最大 5 件) で挙げ、「チケットにコメントする」で残して止まる。ブランチも
PR も作らない。

条件が前提にする画面・API・データ (「〇〇画面で」「一覧から」など) がターゲットブランチに
あるかも、ここで確かめる。無く、それを作ることもチケットに書かれていないなら、実装が
一意に決まらない条件として扱う。前提の欠けた条件は、確認手順の 1 行目で誰も先に
進めなくなる。

条件のどこまで (画面・API・データのどれ) をこのチケットで作るかが本文から読めないときも、
一意に決まらない条件として扱う。「後続のチケットの管轄」と判断して削ることも、条件を
広く読んで兄弟の範囲を足すことも、チケットに書かれなかった範囲を推測で決めることになる。

独断で埋めた仕様は差分の中に紛れる。レビューはコードの誤りは見つけるが、書かれなかった
仕様の誤りは見つけない。

### 4. ブランチを切り、全受け入れ条件に検証を割り振る

ターゲットブランチの最新から、チケット 1 件に 1 ブランチを切る。それから手順 2 の一覧の
受け入れ条件 1 件ごとに次のどれかを割り振る。この対応がそのまま PR 本文の「受け入れ条件と検証」表の
行になる。全条件に割り振りが付くまで手順 5 に進まない。「手間がかかる」は割り振れない
理由にならない。

- **既存テスト** — 条件を検証するテストが既にある。テスト名を控える
- **新規テスト** — 条件が満たされていないことで落ちるテストを書き、実行して落ちることを
  確認する。落ちない、または「未実装だから」以外の理由 (import エラー、設定の不備) で
  落ちるテストは、その条件を検証していない
- **プレースホルダ** — 実装前には落ちるテストが書けない条件 (実装後に生まれる関数や
  エンドポイントを呼ぶものなど)。テストランナーの skip 指定で骨組みだけ置き、手順 6 で
  実装済みのテストに置き換える
- **自動テスト不能** — 次の 3 つのどれかに当たる条件だけ。skip 指定のテストを、区分の
  1 語と具体的な理由を付けて残す。どの区分でも、手順 8 の確認手順を 1 本書く
  - `操作のみ` — 目視や画面の操作でしか確認できない。何を見て判定するのかを理由に書く
  - `対象外` — テスト基盤がその層を実行できない (UI 描画、ネイティブ依存など)。層の話で、
    対象のファイルに既存のテストが無いことはこれに当たらない。実行できない層を名指しする
  - `外部依存` — テスト環境に無い依存を 1 つ名指しする

この 3 語は**自動テストを書かない理由**で、**実行して確かめない理由ではない**。自動テスト
不能に割り振った条件も、手順 6 で確認手順を自分で実行して確かめる。操作はブラウザ操作の
ツールで行えるので、「操作が要る」は人間に渡す理由にならない。実行しない理由は手順 6 の
3 語に限る。

テストが条件を検証したことになるのは、条件の操作を行い、条件の結果を確かめているときだけ。
振る舞いが依存する定義 (ルート定義・定数・設定・型) の中身を確かめるテストは、つなぎの
一部を確かめるだけで、条件は検証していない。「一覧から選択すると遷移する」に対して
ルート定義にパスがあることを確かめても、一覧の項目を選んだときに遷移するかは分からない。

`画面` の印の付いた条件は、下の層のテストに加えて、画面での確かめ方を 1 つ割り振る。
リポジトリのコンポーネントテストや E2E テストで条件の操作 (項目を選ぶ、ボタンを押す) を
行い結果 (遷移先、表示) を確かめるテストが書けるならそれを書き、書けないなら確認手順を
1 本割り振って手順 6 で実行する。下の層のテストだけで `画面` の条件を OK にしない。

画面操作を伴う条件を、条件ごと自動テスト不能に回さない。テストできないのは描画と操作の
層だけで、その下は他の条件と同じく割り振れる。画面がサーバを呼ぶなら、画面側が組み立てる
のと同じパス・メソッド・項目名・型でサーバの受け口を呼ぶテストか、画面側の呼び出し処理を
サーバの定義と突き合わせるテストを書く。呼ぶ側と受ける側が別々に作られると、どちらの
テストも通ったまま、つなぐと動かない。

検証のために一時的なコード変更 (エラーを起こす、分岐を強制する、待ち時間を縮めるなど) が
要る条件は、その変更をテストダブルや設定の差し替えとしてテストの中で行えることが多い。
自動テスト不能に回す前に、それができないかを確かめる。できないときは、その変更を確認手順の
準備に書く。

テストの実行コマンドが無いリポジトリ (CI 設定・パッケージのスクリプト定義・テストランナー
の設定のいずれにも無い) では、この手順を飛ばして全条件を確認手順に割り振り、条件ごとに
確認手順を書く。テスト基盤が無いことは表に書く。基盤は新設しない。

既存のテストは書き換えず、追加で書く。

**テストを書くのは実装の前のここ。** 実装の後に書いたテストは実装をなぞるだけで、
条件を満たしていない実装でも通る。

### 5. 最小の変更を実装する

受け入れ条件を満たす最小の変更にとどめる。スコープ外の改善は入れず、気づいた点は手順 9 の
チケットへのコメントに回す。PR 本文にはスコープ外の気づきのための欄を作らない。

「最小」は変更の範囲のことで、コメントを省くことではない。`artifact-writing` の
「コードコメントを付ける場所」に当たる箇所には、実装と同じコミットで根拠のコメントを付ける。

ユーザーに見える文言を変えたら、手順 6 に進む前に `ui-copy` の手順で画面単位に照合する。
事実に反する文言を直す変更では、条件節や注記を足す前に `ui-copy` の選択肢を順に試す。

### 6. テストを通し、プレースホルダを回収する

手順 4 のテストと既存のテストを実行して通す。テストを通すためにテスト自体を書き換えない。
期待値が誤っていたと分かったときだけ直し、その旨を「自律判断した箇所」に書く。

プレースホルダにした条件は、ここで実装済みのテストに置き換える。期待値は実装の出力を
写さず、受け入れ条件の文言から書く。skip のまま残してよいのは自動テスト不能の 3 語の理由が
付いたものだけで、「実装前に書けなかった」はここでは理由にならない。

自動テスト不能に割り振った条件と、`画面` の条件のうち確認手順を割り振ったものも、
ここで満たしたことを確かめる。skip したテストは落ちない
ので、確かめなければ未実装の条件がそのまま通る。確かめ方は、手順 8 で書く確認手順を
先に書き、それを自分で実行する。書いた手順を実行すれば、手順そのものが実行できるかも
同時に確かめられる。確認手順は人間に渡す作業ではなく、実装担当が先に実行し、人間が
あとで再現するための手順。ここで止まって依頼者に実行を頼まない。

**まず実行する。** 手順を上から順に、人間と同じ操作で実行し、確認の欄に書いたものが
見えることを確かめる。

- コマンド・リクエスト・スクリプトの実行、ログや出力の確認は、その場で実行する
- 画面操作は、次の順にアプリを起動して操作する
  1. **起動** — 起動方法をリポジトリの README・パッケージのスクリプト定義・コンテナ定義から
     探し、バックグラウンドで起動する (`npm run dev > <一時ディレクトリ>/app.log 2>&1 &`
     など)。ポートが応答するまで待ち、応答しなければログの末尾を控える。待機と応答の確認は
     `node` で行う (`fetch` で数秒おきに試すスクリプト)。`curl` や `sleep` を許可していない
     実行環境があり、拒否されたのを起動できなかったと取り違えないため
  2. **操作の手段** — 実行環境にブラウザ操作のツール (MCP のブラウザツールなど) があれば
     それを使う。無ければリポジトリの E2E テストのランナーを使う。どちらも無ければ、
     リポジトリの外の一時ディレクトリに Playwright を入れ (`npm install --prefix <一時
     ディレクトリ> playwright`)、手順どおりに操作する使い捨てのスクリプトを書いて `node` で
     実行する。ブラウザ本体が無ければ `<一時ディレクトリ>/node_modules/.bin/playwright
     install chromium` で入れる。素の `npx playwright` はレジストリの最新版を使い、
     スクリプト側の Playwright と版の違うブラウザが入ることがある
  3. **証拠** — スクリプトに、確認の欄に対応するもの (到達した URL、見えた文言、要素の
     有無) を標準出力へ出させ、スクリーンショットを一時ディレクトリに保存する。出力は
     手順 8 の実行結果にそのまま写す
- 検証のために一時ディレクトリへ入れるツールは、リポジトリの依存にも lockfile にも
  加えないので、「依存パッケージの大規模な追加」には当たらない。リポジトリの
  `package.json` などは変えない
- 画面の操作はサーバとのつなぎ目も通るので、描画から処理までを 1 度に確かめられる。
  コードを読んで確かめるより強いので、実行できるなら読むだけで済ませない

実行して確認の欄どおりに見えた条件は、手順 8 の表で結果を OK にでき、実行したことを
確認手順の実行結果に残す。

**実行できないときだけ、コードでたどる。** 実行できないと言えるのは、上の手段を実際に
試して失敗したときだけで、理由は次の 3 語に限る。どれも試したコマンドと出たエラーを控える。

- `起動不可` — 起動に要る依存 (データベース・外部サービス・認証) が用意できず、アプリが
  起動しない。その依存を名指しする
- `実行手段なし` — 操作の手段を 3 つとも試して使えない
- `外部未接続` — アプリは起動して操作もできるが、条件の結果が実行環境から接続できない
  外部のサービスやハードウェア (実際のメール送信・決済・端末など) で決まる。依存を
  名指しし、足りないもの (認証情報・接続先) を書く。操作できるところまでは実行する

試さずに「画面操作が必要」「手動での確認が必要」とするのは、実行できない理由ではない。
控えたうえで、手順の操作を 1 行ずつ、人間がたどる順にコードでたどる。条件を満たす処理を 1 箇所指すだけでは、そこへ人間が
たどり着けるかは分からない。

- **入口** — 準備と操作に出てくる画面・URL・メニュー・ボタン・入力欄を 1 つずつ、それを
  定義するコード (ルーティング、画面部品、表示される文言) で指す。指せないものは、手順が
  存在しない物を操作させている
- **つなぎ目** — 画面がサーバを呼ぶなら、呼ぶ側と受ける側を両方開いて、パス・メソッド・
  パラメータと項目の名前・型・応答の形が一致することを確かめる。片側だけを読んで確かめた
  ことにしない
- **処理** — 条件の文言どおりに振る舞うことを読んで確かめる

実行して条件に反した条件、入口からつなぎ目を通って処理まで指せない条件は、未検証では
なく**未実装**。
実装を直す。skip は機械で確かめる手段が無いことを示す区分で、条件を満たしていないことを
隠す場所ではない。

実装を直してもテストが通らない、または未実装の条件が残るなら、PR は作らず、手順 3 と
同じ形で何が通らない・満たせないかを残して止まる。

### 7. コミットして push する

変更したファイルを名指しして `git add` し、コミットして push する。push するのは手順 4 で
切ったブランチだけで、ターゲットブランチへは直接 push しない。push 済みのコミットは
書き換えない。まとめ直すなら push の前に済ませる。

### 8. PR を作る

作る前に次の 2 つを順に通す。

- **完了の確認** — 次がすべて成り立つ。欠けたまま作らない
  - 手順 4 の割り振りが全条件に付き、手順 6 のテストが通っている
  - `画面` の印の付いた条件の結果が OK なら、検証方法は条件の操作を行うテストか
    `M 番号 (実行済み)` のどちらか。そうでなければ未検証にする
  - `M 番号 (実行済み)` の手順すべてに実行結果があり、使った手段 (ツール名か実行した
    コマンド) と、確認の欄に対応する出力 (URL・文言など) が写してある
  - 未検証の理由は、手順 6 の実行環境の事情 3 語 (`起動不可` / `実行手段なし` /
    `外部未接続`) のどれかで、試したコマンドと出たエラーが添えてある。手順 4 の 3 語
    (`操作のみ` / `対象外` / `外部依存`) は自動テストを書かない理由なので、未検証の理由に
    使わない。「画面操作が必要」「手動での確認が必要」も理由にならない。手順 6 に戻って
    実行する
  - 画面・入口・遷移先が無い、または操作しても条件どおりにならないのは製品側の事情で、
    未検証の理由にならない。チケットがそれを作ると書いていれば未実装なので直し、
    書いていなければ手順 3 で止まるべきだった条件なので止まる
  - 「受け入れ条件と検証」の表の行が、手順 2 の一覧と件数・順序・原文で 1 対 1 に並ぶ
  - 未検証の行すべてに、理由と試した操作、対応する確認手順、入口から処理までの経路が
    あり、手順 6 で満たしたことを確かめている。形式が揃っていても、満たしていないと
    分かっている条件や、確かめていない条件を未検証として残さない
- **本文の承認** — 「実行文脈による違い」の表のとおり。チャットで承認が得られないなら
  作らない。本文をファイルに残し、承認待ちであることとその置き場所を「チケットに
  コメントする」で残して止まる。ブランチは手順 7 で push 済みなので、承認後に作れば
  成果は失われない

「PR を作る」でチケットに紐づけて作る。紐づいていれば、レビューの工程が受け入れ条件を
読める。

本文の見出しは PR テンプレートを読んでそのまま使い (出力規約)、テンプレートが無ければ
下の 5 つを使う。HTML コメント (`<!-- -->`) は記入後に消す。各欄の書き方は、テンプレートの
有無に関わらず次のとおり。

- **変更概要** — 何を、どう解決したか。**3 行以内**。下のレビュ要点を読むための前置きで
  あって、差分の言い換えではない
- **レビュ要点** — 次の 2 つだけを入れる見出しで、それ自体に本文を書かない
  - **自律判断した箇所** — チケットに指示が無く、自分の判断で決めた点。最大 3 件、
    1 件 1 行、確信が低いものから順に。無ければ「該当なし」と書く
  - **未検証の受け入れ条件** — 下の表で「未検証」とした条件ごとに 1 行、
    `AC 番号 — 起動不可 / 実行手段なし / 外部未接続: 試したコマンドと出たエラー (M 番号)`。
    理由の 1 語だけでは足りない。読み手が知りたいのは、なぜ実装担当が実行できなかったかと、
    自分が何を用意すれば実行できるか。無ければ「該当なし」と書く
- **受け入れ条件と検証** — 手順 2 の一覧の順に、1 条件 1 行の表 (条件 / 検証方法 / 結果)。
  条件の欄は `AC 番号: 原文` で、チケットの文言を写す。一覧に無い行を足さず、一覧の行を
  統合しない。検証方法は差分内のテストのパス (テスト名まで) か、確認手順の M 番号。
  定数名や概念名だけの呼び名 (「ルーティング確認」など) のような、何を実行したのか読み手が
  特定できない書き方をしない。結果は OK / NG / 未検証 のいずれかで、**OK と書けるのは
  実行して確かめたものだけ** — テストを実行して通ったもの、または手順 6 で確認手順を
  自分で実行して確認の欄どおりに見えたもの。後者は検証方法に `M 番号 (実行済み)` と書く。
  未検証の行は消さず、検証方法に skip したテスト名 (`画面` の条件なら、代わりに通した
  下の層のテスト名) と M 番号、手順 6 でたどった経路を入口 → つなぎ目 → 処理の順に
  `path:line` を `→` でつないで書く。未検証は「実行では確かめていないが、実装は条件を満たしている」
  という申告で、人間はその申告を確認手順で確かめる
- **設計判断** — 実装から読み取れないものだけ、最大 3 件、1 件 1 行。「なぜ他の案を採らな
  かったか」が 1 行で書けるものに限る。自明な実装に判断はない。無ければ見出しごと削除する
- **確認手順** — テンプレートの見出しが `手動確認手順` ならその見出しに書く。自動テスト
  不能に割り振った条件と、手順 4 で画面の確かめ方に確認手順を割り振った `画面` の条件
  1 件に 1 本、`M1`、`M2`… と番号を振り、対象の AC 番号を添える。手順 6 で実行して OK に
  した条件の手順も消さない。人間が再現するときの手順になる。割り振った条件が無ければ
  「不要」と書く。各手順に次の 4 つを書く
  - **準備** — 環境・データ・アカウント。検証のための一時的なコード変更が要るなら、変更箇所
    (`path:line`) と最小の差分をここに載せ、この PR には入れないことを明記する。差分は
    コードの引用ではなく操作の指示なので、`output-contract` の引用の制限の対象外
  - **操作** — 番号付きの手順
  - **確認** — どこ (画面・ログ・レスポンス・テーブル) を見て、何が見えれば OK か。条件の
    文言に対応させる

  - **実行結果** — 何で操作し (使ったツール・起動したコマンド・スクリプト)、確認の欄に
    対して何が出力されたか (到達した URL・見えた文言)。実行できなかったなら、試した
    コマンドと出たエラーを書く。どの手順にも書き、空欄にしない

  書き終えたら、この手順だけを読んで、質問せずに OK / NG を判定できるかを確かめる。
  「確認が必要」とだけ書いた手順は、確認する人に調査を丸ごと渡している

変更概要のすぐ下に自律判断と未検証を置くのは、**レビュアーが差分を読んでも分からないのが
そこだけ**だから。人間の注意力は下へ行くほど落ちるので、人間にしか決められないものを
できるだけ上に置く。変更概要が 3 行なのはそのためで、超えた分はそのまま判断材料を
下へ押し下げる。

「該当なし」と書かせるのは自律判断と未検証の 2 つだけ。空欄だと、判断が無かったのか
書き忘れたのかを読み手が区別できない。設計判断は逆に、無ければ見出しごと削除する。
残すと埋めたくなり、埋めるために生成された設計判断は本物を薄める。

### 9. チケットに報告する

「チケットにコメントする」で、PR の URL と 1 行のサマリだけを残す。PR 本文の内容を
チケット側に繰り返さない。両方に書けばどちらかが必ず古くなる。手順 5 でスコープ外に
気づいた点があれば、最大 3 件、1 件 1 行で添える。

サマリと、チャットでの依頼者への報告には、受け入れ条件の件数を結果ごとに添える
(`AC 5 件: OK 3 / 未検証 2 (M1, M2)`)。未検証が 1 件でもあれば「完了」と書かず、
人間の確認待ちと書き、実行できなかった理由 (`起動不可` / `外部未接続` なら足りない依存、
`実行手段なし` なら使えなかった手段) を添える。「完了」とだけ書くと、未検証の条件は誰にも確かめられずに
マージされる。理由を添えるのは、依頼者がそれを用意すれば次は実装担当が実行できるため。

## やらないこと

- ターゲットブランチへの直接 push、force push
- チケットに書かれていない機能の追加
- 受け入れ条件の不足を推測で埋めた実装
- チケットに書かれていない範囲の、後続のチケットへの持ち越しや兄弟のチケットからの取り込み
- チャットで承認を得ていない PR の作成 (ドラフトも作らない)
- 依存パッケージの大規模な追加・更新 (必要ならチケットのコメントで提案に留める)
- テスト基盤・テストフレームワークの新設
- テストを通すためのテスト自体の書き換え
- 実行して通っていないテストを「OK」と報告すること
- チケットの受け入れ条件と 1 対 1 に対応しない検証の表 (統合・言い換え・条件に無い行)
- 試したコマンドと出たエラー、確認手順の無い「未検証」
- 「画面操作が必要」「手動での確認が必要」、または手順 4 の 3 語を、未検証の理由にすること
- 手順 6 の操作の手段を試さずに、確認手順の実行を依頼者に頼んで止まること
- 画面を操作できる環境で、実行せずにコードを読むだけで確認を済ませること
- `画面` の条件を、条件の操作を行わないテスト (ルート定義・定数・設定の確認) だけで OK に
  すること
- 画面・入口・遷移先が無いこと、操作しても条件どおりにならないことを、未検証の
  理由にすること
- 手順の抜けを指摘されて、やり直すかどうかを依頼者に尋ねること
- 実行していない確認手順を「OK」と報告すること
- 満たしていないと分かっている条件、入口から処理までの経路を指せない条件を「未検証」と
  して PR を作ること
- 存在しない画面・操作・API を前提にした確認手順
- 未検証の条件が残る PR を「完了」と報告すること
- PR テンプレートに無いセクションの追加 (出力規約の `確認手順` を除く)
- 「自律判断した箇所」「未検証の受け入れ条件」を空のまま残すこと
- 成果物 (コード・docs) への経緯の記述 (過去形・「以前は」・PR / チケット番号)
- PR の承認・マージ・破棄、チケットの状態の変更 (ワークフローの指示があるときを除く)
