# 実装 — チケットを実装する

チケットを読み、実装し、プルリクエスト (PR) を作るまでの手順。GitHub でも
Azure DevOps でも同じ手順で動く。

## この工程の入口

入口条件: **受け入れ条件の埋まったチケットがあり、PR が無い** (ループの定義は
`dev-loop` スキル)。条件が違う依頼は該当する工程に渡す。

- チケットが無い、または受け入れ条件を書き起こすところから → 設計の工程
- PR のレビュー → レビューの工程、レビュー指摘への対応 → 修正の工程

依頼の中の数字だけのファイル名 (`2251.md` など) や裸の数字はチケット番号である
ことがある。「チケットを読む」で引き当ててから始める。

## 能力層

基盤ごとに違う操作は、この本文に「チケットを読む」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

用語も能力層に合わせて読み替える。**チケット**は GitHub の Issue、Azure DevOps の
作業アイテム。**受け入れ条件**は Azure DevOps では型ごとのフィールド (受け入れ基準、
再現手順など) にあり、どのフィールドかは能力層で調べる。

Git の操作 (branch / commit / push / diff) は `git` CLI を使う。

## 実行文脈による違い

手順は同じで、人間の承認の取り方だけが違う。

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 着手の承認 | 依頼そのもの | 人間の `ai:go` 付与 |
| 条件が足りない・変更が見込みを超える・テストが通らない | チケットにコメントし、依頼者にも伝えて止まる | チケットにコメントし、ワークフローの指示どおりに止まる |
| PR の作成 | タイトル・本文・ブランチを見せて承認を得てから作る | そのまま作る。マージは人間が行う |

チャットで PR の作成に承認を挟むのは、作成がレビュアーへの通知を伴い、エージェントから
取り消せないため。GitHub Actions で挟まないのは、`ai:go` が着手と一緒に作成まで承認して
おり、作られた PR は人間がマージするまで何も進めないため。

チャットで、この手順の抜け (画面を確かめていない、テストが条件を検証していないなど) を
指摘されたら、どうするかを尋ね返さず、抜けた手順まで戻ってやり直す。手順に書かれたことは
依頼の範囲に入っており、改めて承認を得るものではない。やり直した結果、PR 本文と報告を
直してから、何を実行し何が見えたかを伝える。

チケットの状態 (GitHub の状態ラベル `ai:*`、Azure DevOps の `System.State`) は、GitHub
Actions のワークフローが指示したときだけ動かす。チャットからの実行では触らない。種別の
ラベル (`type:*` / `from:*`) は状態ではなく、起票の一部として付けてよい (起点を書き換える
ときの張り替えを含む)。いつ誰が状態を動かすかは運用が決める。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の規約は次の 3 つ。

- PR 本文の**見出し**はリポジトリの PR テンプレートが正典 (置き場所は能力層)。
  足さない・改名しない。見出しの構成はテンプレートが決め、各欄に何をどう書くかはこの
  手順が決める。例外は次の 2 つで、テンプレートに無ければ足す
  - `レビュ要点` (その下の `自律判断した箇所` / `未検証の受け入れ条件`) と
    `受け入れ条件と検証`。手順 9 の完了の確認とレビューの工程が、この欄を読んで
    条件ごとの検証を突き合わせる
  - `成果との差` — `レビュ要点` の下に、手順 9 の成果との照合で差が見つかったときだけ
    足す。条件はすべて満たしたのに成果に届いていないことは、差分にも検証の表にも現れない
  - `確認手順` — 手順 7 の対象の条件があるのに、テンプレートに確認手順の欄 (`確認手順` /
    `手動確認手順`) が無いとき。手順が無ければ、誰もその条件を実行して確かめられない
- PR 本文は折りたたみの外を **合計 25 行以内**。実装量が多くても本文は増やさない。
  ただし「受け入れ条件と検証」の表と「確認手順」はこの上限の外に置く。どちらも
  条件の数だけ要る欄で、削った分は人間が質問して取り戻すことになる
- 変更ファイルを列挙しない。PR の画面が既に表示している

## 手順

### 1. 規約を読む

- リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
  従う
- コードを変更するとき、コミットする成果物 (docs / README / ADR / コードコメント / 型定義)
  を書くときは `artifact-writing` スキルに従う。成果物は現在形で書き、そこに至った経緯は
  PR 本文へ移す。コメントを付ける場所は `artifact-writing` の「コードコメントを付ける場所」に従う
- ブランチ名とコミットメッセージは `git-conventions` スキルに従う
- ユーザーに見える文言を足す・変える・消すなら `ui-copy` スキルに従う。文言規約の場所は
  上の規約ファイルが指している

### 2. 満たすべき条件を読む

「チケットを読む」で本文とコメントを読む。本文より新しい決定がコメントに残っていることが
ある。「親チケットを読む」で親があれば読む。チケット 1 件には「何を」しか書かれておらず、
「なぜ」は親にある。

読んだ受け入れ条件を、番号付きの一覧 (`AC1`、`AC2`…) に書き出す。この一覧が手順 4 の
割り振りと、手順 9 の表の行になる。

- チケットに書かれた単位 (チェックボックス・箇条書き・番号・改行) で 1 件とする。区切りの
  無い散文なら文ごとに区切る。統合・言い換え・要約をせず、本文は原文のまま写す
- コメントで条件が追加・変更されていれば、その件も一覧に入れ、出典のコメントの日付を添える
- 実装の都合で生まれた項目 (ビルドが通る、既存のテストが通るなど) は条件ではないので
  入れない
- 利用者が画面で操作するか、画面に見えることで判定する条件 (「選択すると」「押すと」
  「遷移する」「表示される」など) に `画面` の印を付ける。印は条件の文言だけで決め、
  変更したファイルが画面側かサーバ側かでは決めない。印の付いた条件は手順 4・7・9 で
  画面の確認が要る

一覧の頭には、このチケットの成果 (成果の見出しが無ければ背景・目的) を写す。親の成果は
写さない。受け入れ条件は
成果が達成されたかを確かめるための標本で、条件をすべて満たしても成果に届かないことがある。
手順 9 で、作った物をこの成果に照らす。

一覧はリポジトリの外 (一時ディレクトリ) にファイルとして書き出し、手順 4 と手順 9 は
そこから作る。実装を挟むうちに、条件の記憶は作った物の記憶に置き換わっていく。

### 3. 条件が足りないか、変更が見込みを超えるなら止まる

受け入れ条件が空、または実装が一意に決まらないなら、推測で実装しない。不足している
条件を 1 件 1 行 (最大 5 件) で挙げ、「チケットにコメントする」で残して止まる。ブランチも
PR も作らない。

条件が前提にする画面・API・データ (「〇〇画面で」「一覧から」など) がターゲットブランチに
あるかも、ここで確かめる。ターゲットブランチは、依頼・チケット・リポジトリの規約が
指定していればそのブランチ、指定が無ければリポジトリの既定ブランチ。前提が無く、それを作ることもチケットに書かれていないなら、実装が
一意に決まらない条件として扱う。前提の欠けた条件は、確認手順の 1 行目で誰も先に
進めなくなる。

条件のどこまで (画面・API・データのどれ) をこのチケットで作るかが本文から読めないときも、
一意に決まらない条件として扱う。「後続のチケットの管轄」と判断して削ることも、条件を
広く読んで兄弟の範囲を足すことも、チケットに書かれなかった範囲を推測で決めることになる。

独断で埋めた仕様は差分の中に紛れる。レビューはコードの誤りは見つけるが、書かれなかった
仕様の誤りは見つけない。

条件が一意に決まっていても、満たすための変更が見込みより大きいときも止まる。手順 2 の
一覧の各行に、満たす手段を 1 行書き足す。見込みは、設計の検討記録の
`条件 — 手段 — 変更の規模` の行と、それより新しいコメントで人間が認めた手段・選んだ条件。
手段は見込みどおりでなくてよく、比べるのは変更の規模だけ。次のどちらかに当たれば、作らずに
止まる。

- 見込みに無い仕組みを新しく作る、または見込みに無い領域 (画面・API・ジョブ・データ) まで
  変わる
- 見込みが無く、チケットに書かれていない仕組みを新しく作らないと満たせない。仕組みは既存に
  同種の無い構成要素 (新しいテーブル・常駐処理・キュー・キャッシュ・新しい外部サービスとの
  接続) で、既存のテーブルへの列の追加や既存の連携の利用は含まない

止まるときは、該当する条件ごとに、要る手段と変更の規模、成果を満たす範囲で手段の小さい
代わりの条件を挙げ、「条件を残して規模を認める」「代わりの条件にする」のどちらかに推奨を
付けて「チケットにコメントする」で残す。人間の回答のコメントが、その条件の新しい見込みに
なる。どこまでの振る舞いに費用を払うかは人間が決めることで、実装は大きな仕組みを作り込む
ことも、条件を黙って縮めることもしない。手順 5 の途中で規模の超過が分かったときも、ここに
戻って同じく止まる。

### 4. ブランチを切り、全受け入れ条件に検証を割り振る

ターゲットブランチの最新から、チケット 1 件に 1 ブランチを切る。それから手順 2 の一覧の
受け入れ条件 1 件ごとに次のどれかを割り振る。この対応がそのまま PR 本文の「受け入れ条件と検証」表の
行になる。全条件に割り振りが付くまで手順 5 に進まない。「手間がかかる」は割り振れない
理由にならない。

- **既存テスト** — 条件を検証するテストが既にある。テスト名を控える
- **新規テスト** — 条件が満たされていないことで落ちるテストを書き、実行して落ちることを
  確認する。落ちない、または「未実装だから」以外の理由 (import エラー、設定の不備) で
  落ちるテストは、その条件を検証していない
- **プレースホルダ** — 実装前には落ちるテストが書けない条件 (実装後に生まれる関数や
  エンドポイントを呼ぶものなど)。テストランナーの skip 指定で骨組みだけ置き、手順 6 で
  実装済みのテストに置き換える
- **削除の確認** — 前提を伴わず、コード・フィールド・画面の項目・設定・API・文言を
  無くすことそのものが条件のもの (「不要な〇〇を削除する」「〇〇が表示されない」)。
  「存在しないこと」だけを確かめるテストは書かない。代わりに、対象を一意に指す語
  (識別子・別表記・i18n キー・全ロケールの文言) を、削除の範囲 (リポジトリ全体、または
  対象を消す画面・モジュールのファイル) に絞って検索するコマンドを手順 5 の前に実行し、
  該当する件数を控える。実装前に該当しないコマンドは何も確かめないので使えない。手順 6 で
  同じコマンドが該当なしになれば OK。履歴として残す箇所 (過去のマイグレーション、この変更で
  足す削除のマイグレーション、CHANGELOG) を除くなら、除外をコマンドに含める。対象が名前で
  追えないとき (定義から動的に作られる画面の項目、一般的な語で別物に当たるラベル) と、定義
  だけでは実際の出力が決まらないとき (DB の列、応答の項目) だけ、検索に代えて確認手順を
  1 本割り振り、検証方法は `M 番号 (実行済み)` と書く
- **自動テスト不能** — 次の 3 つのどれかに当たる条件だけ。skip 指定のテストを、区分の
  1 語と具体的な理由を付けて残し、確認手順を 1 本割り振る
  - `操作のみ` — 目視や画面の操作でしか確認できない。何を見て判定するのかを理由に書く
  - `対象外` — テスト基盤がその層を実行できない (UI 描画、ネイティブ依存など)。層の話で、
    対象のファイルに既存のテストが無いことはこれに当たらない。実行できない層を名指しする
  - `外部依存` — テスト環境に無い依存を 1 つ名指しする

この 3 語は**自動テストを書かない理由**で、確かめない理由ではない。確認手順を割り振った
条件は、手順 7 で自分で実行する。

テストは、将来も守り続ける振る舞いにだけ書く。削除の確認はこの例外で、無条件に消した
対象の不在は守り続ける理由が無いので、その場限りの検索で足りる。削除の確認以外の条件は、
上の割り振りのとおりテストか確認手順を割り振る。

次のどれかに当たる不在は、削除ではなく残り続ける振る舞いなので、削除の確認にせず、他の
条件と同じく新規テストを割り振る。どれに当たるかは、条件の文言に加えて手順 2 で読んだ
背景・親チケットと、消す対象そのものから判断する。

- 権限や状態を前提にする (「権限が無いとき〇〇が出ない」)
- 消す対象が個人情報・秘密情報か、消す理由がセキュリティ (「応答に個人情報を含まない」)。
  理由が書かれていなくても、対象が個人情報・秘密情報ならこれに当たる
- 旧い入力を送る呼び出し側が残る (「旧項目を受け取っても無視する」)。テストは不在ではなく、
  旧い入力を受けたときの振る舞いを確かめる
- 制約・検証・制限を外し、それによってできるようになる操作がある (「〇〇を必須から外す」
  「件数の上限を撤廃する」)。テストは不在ではなく、できるようになった操作を確かめる

テストが条件を検証したことになるのは、条件の操作を行い、条件の結果を確かめているときだけ。
振る舞いが依存する定義 (ルート定義・定数・設定・型) の中身を確かめるテストは、つなぎの
一部を確かめるだけで、条件は検証していない。「一覧から選択すると遷移する」に対して
ルート定義にパスがあることを確かめても、一覧の項目を選んだときに遷移するかは分からない。

`画面` の印の付いた条件は、下の層のテストに加えて、画面での確かめ方を 1 つ割り振る。
リポジトリのコンポーネントテストや E2E テストで条件の操作 (項目を選ぶ、ボタンを押す) を
行い結果 (遷移先、表示) を確かめるテストが書けるならそれを書き、書けないなら確認手順を
1 本割り振る。下の層のテストだけで `画面` の条件を OK にしない。ただし、削除の確認を
割り振り、検索で確かめられる条件は、`画面` の印が付いていても画面での確かめ方を別に
割り振らない。名前で追えない画面の項目は、削除の確認に書いたとおり確認手順を割り振る。

画面操作を伴う条件を、条件ごと自動テスト不能に回さない。テストできないのは描画と操作の
層だけで、その下は他の条件と同じく割り振れる。画面がサーバを呼ぶなら、画面側が組み立てる
のと同じパス・メソッド・項目名・型でサーバの受け口を呼ぶテストか、画面側の呼び出し処理を
サーバの定義と突き合わせるテストを書く。呼ぶ側と受ける側が別々に作られると、どちらの
テストも通ったまま、つなぐと動かない。

検証のために一時的なコード変更 (エラーを起こす、分岐を強制する、待ち時間を縮めるなど) が
要る条件は、その変更をテストダブルや設定の差し替えとしてテストの中で行えることが多い。
自動テスト不能に回す前に、それができないかを確かめる。できないときは、その変更を確認手順の
準備に書く。

テストの実行コマンドが無いリポジトリ (CI 設定・パッケージのスクリプト定義・テストランナー
の設定のいずれにも無い) では、この手順を飛ばして全条件に確認手順を割り振る。テスト基盤が
無いことは表に書く。基盤は新設しない。

既存のテストは書き換えず、追加で書く。例外は `ui-copy` の「文言を固定したテスト」に
当たるテストと、削除した対象を前提にしていたテスト (残る振る舞いの検証を保って直す。
消してよいのは、削除した対象そのものだけを検証していたテストに限る)。

**テストを書くのは実装の前のここ。** 実装の後に書いたテストは実装をなぞるだけで、
条件を満たしていない実装でも通る。

### 5. 最小の変更を実装する

受け入れ条件を満たす最小の変更にとどめる。スコープ外の改善は入れず、気づいた点は手順 10 の
チケットへのコメントに回す。PR 本文にはスコープ外の気づきのための欄を作らない。

「最小」は変更の範囲のことで、コメントを省くことではない。`artifact-writing` の
「コードコメントを付ける場所」に当たる箇所には、実装と同じコミットで根拠のコメントを付ける。

ユーザーに見える文言を変えたら、手順 6 に進む前に `ui-copy` の手順で画面単位に照合する。
事実に反する文言を直す変更では、条件節や注記を足す前に `ui-copy` の選択肢を順に試す。

### 6. テストを通し、プレースホルダを回収する

手順 4 のテストと既存のテストを実行して通す。削除の確認を割り振った条件は、手順 4 の
コマンドを再実行して結果を控え、該当が残るなら実装を直す。テストを通すためにテスト自体を
書き換えない。直してよいのは、期待値の誤りが分かったテストと、`ui-copy` の「文言を固定した
テスト」に当たるテスト、削除した対象を前提にしていたテストだけで、直したテストと理由を
「自律判断した箇所」に書く。

プレースホルダにした条件は、ここで実装済みのテストに置き換える。期待値は実装の出力を
写さず、受け入れ条件の文言から書く。skip のまま残してよいのは自動テスト不能の 3 語の理由が
付いたものだけで、「実装前に書けなかった」はここでは理由にならない。

実装を直してもテストが通らないなら、PR は作らず、手順 3 と同じ形で何が通らないかを残して
止まる。

テストが通っても、確認手順を割り振った条件はまだ何も確かめていない。skip したテストは
落ちず、下の層のテストは画面を操作しない。手順 7 に進む。

### 7. 確認手順を実行する

**対象** — 手順 4 で確認手順を割り振った条件 (自動テスト不能の条件、画面の確かめ方に
確認手順を割り振った `画面` の条件、名前で追えないか出力が定義で決まらないため確認手順を
割り振った削除の条件)。対象が 1 件も無いときだけ、この手順を飛ばす。

**成果物** — 一時ディレクトリの実行記録 (手順 2 の一覧の隣に `verify.md` など)。対象の
条件 1 件に 1 節、次の 4 つを書く。**全対象の節がそろうまで手順 8 に進まない。** 手順 9 の
確認手順と表の結果は、ここから写す。

1. 確認手順 — 準備 / 操作 / 確認 (書き方は手順 9 の「確認手順」)。先に書き、それを実行する
2. 手段 — 使ったツール名、起動したコマンド、実行したスクリプトのパス
3. 出力 — 確認の欄に対応するもの (到達した URL・見えた文言・要素の有無) とスクリーンショットのパス
4. 判定 — OK / 未実装 / 実行できない (理由の 1 語、試したコマンドと出たエラー)

確認手順は人間に渡す作業ではない。実装担当が先に実行し、人間があとで再現するための手順。
ブラウザ操作のツールで操作できるので、「画面操作が要る」は依頼者に頼んで止まる理由に
ならない。コマンド・リクエスト・ログの確認だけで済む手順は、その場で実行して 7-4 に進む。
画面の操作は次の 1〜4 の順で行う。

#### 7-1. 起動する

1. 起動方法をリポジトリの README・パッケージのスクリプト定義・コンテナ定義から探す
2. **起動の前に**、アプリが使う DB の接続先を設定ファイルや環境変数で確かめる。起動
   スクリプトはマイグレーションやシードを流したり、セッションやログを書いたりする。
   接続先が共有環境や本番なら、実行環境の中で DB を起動し (コンテナ定義の DB サービス、
   ローカル用の設定、一時的な環境変数の上書き)、マイグレーションを当て、アプリの接続先を
   そちらに向ける。それができなければ、アプリを起動せずに `起動不可` とする。このときは
   7-2 のどの方法でも書き込まず、応答の差し替えでも代えない
3. バックグラウンドで起動する (`npm run dev > <一時ディレクトリ>/app.log 2>&1 &` など)
4. ポートが応答するまで `node` で待つ (`fetch` で数秒おきに試すスクリプト)。`curl` や `sleep`
   を許可しない実行環境があり、その拒否を起動の失敗と取り違えないため。応答しなければ
   ログの末尾を控える

#### 7-2. データを作る

条件の操作に要るデータ (レコード・ユーザー・状態) は自分で作る。7-1 で確かめた実行環境の
中の DB に、次の順に試す。

1. リポジトリのシード・フィクスチャ・ファクトリ (`db:seed` などのスクリプト定義、`seeds/`・`fixtures/`)
2. 起動したアプリの画面や API から作る (ユーザーを登録してログインし、レコードを作る)。
   外部から届くデータも、受け口 (webhook など) へ自分でリクエストを送って作る
3. DB へ直接入れる (使い捨ての SQL やスクリプト)。画面や API から作りにくい状態 (期限切れ・
   大量の件数・他のユーザーの所有物など) は、作ってから値を書き換える

作り方は実行記録の準備に書き、スクリプトは一時ディレクトリに置いて PR には入れない。

画面側でサーバの応答を差し替える (Playwright のリクエストの差し替えなど) のは、上の 3 つを
試してもデータを作れなかったときだけ。差し替えた応答はサーバを通らず、画面とサーバの
つなぎ目は確かめていない。どのリクエストを何に差し替えたかを出力に書き、そこから先は
下の「コードでたどる」で確かめる。

#### 7-3. 操作する

次の順に、使える最初の手段で、確認手順の操作を上から人間と同じ順に行う。

1. 実行環境のブラウザ操作のツール (MCP のブラウザツールなど)
2. リポジトリの E2E テストのランナー
3. 一時ディレクトリに入れた Playwright。`npm install --prefix <一時ディレクトリ> playwright`
   で入れ、ブラウザ本体が無ければ `<一時ディレクトリ>/node_modules/.bin/playwright install
   chromium` で入れる (素の `npx playwright` は版の違うブラウザを入れることがある)。手順どおりに
   操作する使い捨てのスクリプトを書き、`node` で実行する

スクリプトには、確認の欄に対応するもの (URL・文言・要素の有無) を標準出力へ出させ、
スクリーンショットを一時ディレクトリに保存させる。その出力を実行記録に写す。

一時ディレクトリに入れたツールはリポジトリの依存にも lockfile にも加えないので、
「依存パッケージの大規模な追加」に当たらない。`package.json` などは変えない。

#### 7-4. 判定する

- **確認の欄どおりに見えた** → OK。手順 9 の表で `M 番号 (実行済み)` と書ける
- **条件に反した**、または画面・入口・遷移先が無い → 未実装。実装を直して手順 6 からやり直す。
  チケットがその画面や入口を作ると書いていなければ、手順 3 で止まるべきだった条件なので止まる
- **実行できない** → 理由は下の未検証の理由の 3 語に限り、7-1〜7-3 の手段を実際に試して
  失敗したときだけ使える。試したコマンドと出たエラーを控える。データが無いだけなら 7-2 で
  作る。`外部未接続` でも、操作できるところまでは実行する

未検証の理由の 3 語:

<!-- unverified-reasons:begin -->
- `起動不可` — 起動に要る依存 (DB・外部サービス・認証) が用意できず、アプリが起動しない。
  依存を名指しする。DB の接続先が共有環境や本番のものしか無く、実行環境の中で DB を
  起動できない (コンテナ定義・ローカル用の設定・環境変数の上書きを試して失敗した) ときも
  これ。アプリが起動して、条件に合うデータが無いだけなら起動不可ではない
- `実行手段なし` — ブラウザ操作のツール・リポジトリの E2E テストのランナー・一時ディレクトリに
  入れた Playwright のどれも試して使えない
- `外部未接続` — 起動と操作はできるが、結果が実行環境から接続できない外部のサービスや
  ハードウェア (実際のメール送信・決済・端末など) で決まる。依存と足りないもの
  (認証情報・接続先) を名指しする
<!-- unverified-reasons:end -->

試さずに「画面操作が必要」「手動での確認が必要」「検証データが用意できない」とするのは、
実行できない理由ではない。7-1 に戻る。

**実行できないときだけ、コードでたどる。** 確認手順の操作を 1 行ずつ、人間がたどる順に
たどる。条件を満たす処理を 1 箇所指すだけでは、そこへ人間がたどり着けるかは分からない。

- **入口** — 準備と操作に出てくる画面・URL・メニュー・ボタン・入力欄を 1 つずつ、それを
  定義するコード (ルーティング、画面部品、表示される文言) で指す
- **つなぎ目** — 画面がサーバを呼ぶなら、呼ぶ側と受ける側を両方開いて、パス・メソッド・
  パラメータと項目の名前・型・応答の形が一致することを確かめる
- **処理** — 条件の文言どおりに振る舞うことを読んで確かめる

入口からつなぎ目を通って処理まで指せた条件だけが未検証になる。指せない条件は未実装で、
実装を直して手順 6 からやり直す。直しても未実装の条件が残るなら、PR は作らず、手順 3 と
同じ形で何が満たせないかを残して止まる。

### 8. コミットして push する

変更したファイルを名指しして `git add` し、コミットして push する。push するのは手順 4 で
切ったブランチだけで、ターゲットブランチへは直接 push しない。push 済みのコミットは
書き換えない。まとめ直すなら push の前に済ませる。

### 9. PR を作る

作る前に次の 3 つを順に通す。

- **完了の確認** — 次がすべて成り立つ。欠けたまま作らない
  - 手順 4 の割り振りが全条件に付き、手順 6 のテストが通っている
  - 手順 7 の対象すべてに実行記録の節があり、4 つが埋まっている。無ければ手順 7 に戻る
  - `画面` の条件を OK にした検証方法は、条件の操作を行うテスト、`M 番号 (実行済み)`、
    削除の確認のいずれか
  - 未検証の理由は手順 7 の 3 語 (`起動不可` / `実行手段なし` / `外部未接続`) のどれかで、
    試したコマンドと出たエラー、入口から処理までの経路が添えてある。手順 4 の 3 語は
    自動テストを書かない理由なので使わない
  - 「受け入れ条件と検証」の表の行が、手順 2 の一覧と件数・順序・原文で 1 対 1 に並ぶ
- **成果との照合** — 手順 2 の一覧の成果を 1 件ずつ、条件の側からではなく成果の側から
  読み、この実装でその成果が達成されるかを確かめる。照らすのはこのチケットの成果だけで、
  親の成果には照らさない。条件に書かれなかった画面・場合・つなぎ目のせいで届いていないと
  読めるものを、差として挙げる。このチケットのスコープ外か、兄弟のチケットの成果で説明が
  つくものは差にしない。差はこの PR では埋めない。
  チケットに書かれていない振る舞いを足すと、書かれなかった仕様が差分に紛れる。差は PR
  本文の「成果との差」と手順 10 の報告に書き、条件を足すか別のチケットにするかは設計の
  工程が決める
- **本文の承認** — 「実行文脈による違い」の表のとおり。チャットで承認が得られないなら
  作らない。承認待ちであることと PR の本文を「チケットにコメントする」で残して止まる。
  本文は `<details>` に畳み、折りたたみの使えない基盤では承認待ちの 1 行の後に区切りを
  置いて続ける。ブランチは手順 8 で push 済みなので、承認後にその本文で作れば成果は
  失われない

「PR を作る」でチケットに紐づけて作る。紐づいていれば、レビューの工程が受け入れ条件を
読める。

本文の見出しは PR テンプレートを読んでそのまま使い (出力規約)、テンプレートが無ければ
下の 5 つを使う。HTML コメント (`<!-- -->`) は記入後に消す。各欄の書き方は、テンプレートの
有無に関わらず次のとおり。

- **変更概要** — 何を、どう解決したか。**3 行以内**。下のレビュ要点を読むための前置きで
  あって、差分の言い換えではない
- **レビュ要点** — 次の 2 つ (差があれば「成果との差」も) だけを入れる見出しで、それ
  自体に本文を書かない
  - **自律判断した箇所** — チケットに指示が無く、自分の判断で決めた点。最大 3 件、
    1 件 1 行、確信が低いものから順に。無ければ「該当なし」と書く
  - **未検証の受け入れ条件** — 下の表で「未検証」とした条件ごとに 1 行、
    `AC 番号 — 起動不可 / 実行手段なし / 外部未接続: 試したコマンドと出たエラー (M 番号)`。
    理由の 1 語だけでは足りない。読み手が知りたいのは、なぜ実装担当が実行できなかったかと、
    自分が何を用意すれば実行できるか。無ければ「該当なし」と書く
  - **成果との差** — 手順 9 の成果との照合で見つかった差。`未検証の受け入れ条件` の後に、
    同じ階層の見出しで置く。1 件 1 行、
    `成果 — 届いていないもの (条件に無かった画面・場合・つなぎ目)`、最大 3 件。差が無ければ
    見出しごと書かない
- **受け入れ条件と検証** — 手順 2 の一覧の順に、1 条件 1 行の表 (条件 / 検証方法 / 結果)。
  条件の欄は `AC 番号: 原文` で、チケットの文言を写す。一覧に無い行を足さず、一覧の行を
  統合しない。検証方法は差分内のテストのパス (テスト名まで) か、確認手順の M 番号か、
  削除の確認のコマンドとターゲットブランチでの件数
  (``削除確認 `grep -rnw memo src/edit` (ターゲットブランチで 3 件)``。
  語の OR は `-e` を並べて書き、パイプでつながない。表の `|` と衝突する)。
  定数名や概念名だけの呼び名 (「ルーティング確認」など) のような、何を実行したのか読み手が
  特定できない書き方をしない。結果は OK / NG / 未検証 のいずれかで、**OK と書けるのは
  実行して確かめたものだけ** — テストを実行して通ったもの、手順 7 で確認の欄どおりに
  見えたもの、削除の確認のコマンドがターゲットブランチでは該当し、この PR のブランチでは
  該当しないもの。手順 7 で確かめたものは、検証方法に `M 番号 (実行済み)` と書く。1 件に
  並べた結果は、すべてを確かめて OK になる。一部でも確かめていなければ、その行は未検証にする。
  未検証の行は消さず、検証方法に skip したテスト名 (`画面` の条件なら、代わりに通した
  下の層のテスト名) と M 番号、手順 7 でたどった経路を入口 → つなぎ目 → 処理の順に
  `path:line` を `→` でつないで書く。未検証は「実行では確かめていないが、実装は条件を満たしている」
  という申告で、人間はその申告を確認手順で確かめる
- **設計判断** — 実装から読み取れないものだけ、最大 3 件、1 件 1 行。「なぜ他の案を採らな
  かったか」が 1 行で書けるものに限る。自明な実装に判断はない。無ければ見出しごと削除する
- **確認手順** — テンプレートの見出しが `手動確認手順` ならその見出しに書く。手順 7 の
  対象 1 件に 1 本、`M1`、`M2`… と番号を振り、対象の AC 番号を添える。OK にした条件の
  手順も消さない。人間が再現するときの手順になる。対象が無ければ「不要」と書く。各手順に
  次の 4 つを、手順 7 の実行記録から写す
  - **準備** — 環境・データ・アカウントを、手順 7 で実装担当が用意したやり方で書く (使った
    シードのコマンド、画面や API での作り方、使い捨ての SQL やスクリプトの中身)。人間に
    用意を頼む欄ではなく、人間がそのとおりに再現するための欄。検証のための一時的な
    コード変更が要るなら、変更箇所 (`path:line`) と最小の差分をここに載せ、この PR には
    入れないことを明記する。差分とデータを作るスクリプトの中身は、コードの引用ではなく
    操作の指示なので、`output-contract` の引用の制限の対象外
  - **操作** — 番号付きの手順
  - **確認** — どこ (画面・ログ・レスポンス・テーブル) を見て、何が見えれば OK か。条件の
    文言に対応させる
  - **実行結果** — 実行記録の手段と出力 (到達した URL・見えた文言)。実行できなかったなら、
    試したコマンドと出たエラー。どの手順にも書き、空欄にしない

  書き終えたら、この手順だけを読んで、質問せずに OK / NG を判定できるかを確かめる。
  「確認が必要」とだけ書いた手順は、確認する人に調査を丸ごと渡している

変更概要のすぐ下に自律判断と未検証 (と成果との差) を置くのは、**レビュアーが差分を読んでも
分からないのがそこだけ**だから。人間の注意力は下へ行くほど落ちるので、人間にしか決められないものを
できるだけ上に置く。変更概要が 3 行なのはそのためで、超えた分はそのまま判断材料を
下へ押し下げる。

「該当なし」と書かせるのは自律判断と未検証の 2 つだけ。空欄だと、判断が無かったのか
書き忘れたのかを読み手が区別できない。設計判断は逆に、無ければ見出しごと削除する。
残すと埋めたくなり、埋めるために生成された設計判断は本物を薄める。

### 10. チケットに報告する

「チケットにコメントする」で、PR の URL と 1 行のサマリだけを残す。PR 本文の内容を
チケット側に繰り返さない。両方に書けばどちらかが必ず古くなる。手順 5 でスコープ外に
気づいた点があれば、最大 3 件、1 件 1 行で添える。

成果との差があれば、別のコメントを「チケットにコメントする」で親 (親が無ければこの
チケット) に残す。先頭行を `成果との差 (#n)` (n はこのチケット) にし、PR 本文と同じ行を
続ける。このチケットは PR のマージで閉じるので、差を受け取る分解・チケットレビュー・設計の
工程は親を読む。PR 本文と重なるが、差の正はこのコメントで、PR 本文の欄は PR の時点の
記録として直さない。

サマリと、チャットでの依頼者への報告には、受け入れ条件の件数を結果ごとに添える
(`AC 5 件: OK 3 / 未検証 2 (M1, M2)`)。未検証が 1 件でもあれば「完了」と書かず、
人間の確認待ちと書き、実行できなかった理由 (`起動不可` / `外部未接続` なら足りない依存、
`実行手段なし` なら使えなかった手段) を添える。「完了」とだけ書くと、未検証の条件は誰にも確かめられずに
マージされる。理由を添えるのは、依頼者がそれを用意すれば次は実装担当が実行できるため。

## やらないこと

- ターゲットブランチへの直接 push、force push
- チケットに書かれていない機能の追加
- 受け入れ条件の不足を推測で埋めた実装
- 手順 3 の変更の規模の超過に当たる仕組みの作り込みと、条件を黙って縮めた実装
- チケットに書かれていない範囲の、後続のチケットへの持ち越しや兄弟のチケットからの取り込み
- チャットで承認を得ていない PR の作成 (ドラフトも作らない)
