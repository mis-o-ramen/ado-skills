# UI 文言 — 変えた文言を基礎の原則・規約と画面で照合する

差分がユーザーに見える文言を足す・変える・消すときに、その差分を基礎の原則とプロジェクトの
文言規約に照合する手順。実装・レビュー・修正のどの工程から読んでも同じ手順を使う。

文言の問題は、文字列を 1 つずつ見ても見つからない。同じ留保の繰り返しや、見出しとボタンの
言い直しは、同じ画面に並ぶ文言をまとめて見たときにだけ現れる。

## 基礎の原則

UI 文言を職業として書く人の間で共通する原則。プロジェクトに文言規約が無くても常に当てる。

1. **利用者の言葉で呼ぶ。** 物・操作は、利用者がふだんその物を呼ぶ言葉で呼び、システムの
   言葉 (内部の呼び名・処理の名前) で呼ばない。避けられない専門用語は初めて出る箇所で説明し、
   対象の利用者が知っている専門用語はそのまま使う。
   利用者は自分の言葉で画面を読み、システムの見方を知らない
2. **1 つの物・操作は、全画面で 1 つの名前で呼ぶ。** 表記も 1 つに揃える。名前が変わると、
   利用者は別の物だと読む
3. **大事なことを先に書き、1 文に 1 つのことだけを書き、同じことを二度言わない。** 見出しや
   ボタンが言ったことを本文で言い直さない。利用者は文の頭と見出し・ボタンだけを拾い読みする
4. **起きたことと確かさを、事実の範囲で言う。** 結果の確かさを実際より強く言い切らず、知り
   得ない原因を断定せず、進んでいない処理を進んだように見せない。言い切った文言を利用者は
   そのまま信じて行動する
5. **エラーは、何が起きたか・分かれば原因・どうすればよいかを書く。** 利用者を責める言い方
   (「不正な」「〜していません」) と内部のコードは出さない。直し方の無いエラーは利用者を
   行き止まらせる
6. **ボタンは、押すと何が起きるかを具体的な動作で名付ける。** 「OK」「はい」「送信」で
   済ませず、確認の画面のボタンは実行する操作の名前にする。ボタンだけを読んで押すかを決める
   利用者がいる
7. **仕組みや操作の手つきではなく、利用者の目的と結果で書く。** ラベルは手つき (「スワイプ」
   「長押し」) や内部の処理ではなく、利用者が得る結果 (「削除」「保存」) を言う。仕組みを
   知らない利用者には、手つきや処理の説明から目的が読めない
8. **位置・色・形だけで物を指さない** (WCAG 1.3.3)。「下の」「右の」「赤い」ではなく、
   物の名前かラベルの文字で指す。読み上げの利用者と、幅で配置が変わる画面には位置が通じない
9. **読み上げで同じ意味が伝わるようにする。** 読み上げ名は見えるラベルと揃え、リンクの文は
   単独で行き先が分かるようにし、要素の種類 (「ボタン」) を名前に入れない。読み上げの利用者は
   画面の配置を見ずに文言だけを聞く
10. **語調を状況と事の重さに合わせ、声は変えない。** 失敗・削除・支払いの場面で冗談や軽い
    言い方をしない。同じ製品の中で人格が変わると、利用者は別の製品のように感じる

UI 文言が日本語のときは、次も当てる。

- 敬語を重ねない (「させていただく」「ご〜いただけますようお願いいたします」)。重ねた敬語は
  内容を埋もれさせる
- 漢字・平仮名・カタカナ語、全角・半角、送り仮名の表記を揃える。表記の揺れは別の語に見える
- 格助詞を省かず (「項目名を変更」)、誰がする動作かを文から読めるようにする。日本語は主語を
  省いても文が成り立つため、アプリがしたことか利用者に頼むことかが曖昧になりやすい
- 二重否定を使わない。「〜しないわけではない」は「〜することもある」と書く

## 規約との関係

プロジェクトの文言規約は、基礎の原則を具体化し (呼び名と表記の表、用語の対応)、資料によって
扱いが割れる点を決める。割れる点は、語調と人格、冗談・謝罪・依頼の言い方 (「すみません」
「〜してください」)、ボタンの語の形 (動詞か名詞か)、文や見出しの長さの数値の基準。

- 規約が具体化した点と割れる点では、規約に従う
- 規約の規則が、具体化にも割れる点にも当たらない形で基礎の原則と食い違うときは、基礎の原則に
  従う
- 規約が基礎の原則の 4 (事実と確かさ) と 9 (読み上げ) を緩める規則を持っていても、その
  2 つは基礎の原則に従う。この 2 つは利用者の判断と利用できるかどうかを左右する
- 割れる点のうち規約が定めていないものは、既存の画面の言い方に揃え、指摘しない。揃える先の
  既存の画面が無いときは、差分の中で 1 つに揃っているかだけを見る

## 1. 文言の変更を見つける

**ユーザーに見える文言**は、画面・通知・メールとして利用者に表示される文字列を指す。

- 入る: コンポーネントやテンプレートのテキスト、文言リソース・翻訳ファイル、文面を組み立てる
  関数の戻り値、利用者に表示されるエラーメッセージ、`aria-label` などの読み上げテキスト
- 入らない: ログ、内部の例外メッセージ、コードコメント、テストの中の文字列

差分の追加・削除行にある文字列リテラルとテキストを拾い、表示に届くかを参照元で確かめる。
届くものが 1 つでもあれば、この手順の 2 以降を通す。無ければここで終わる。

## 2. 文言規約を読む

リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` が文言規約の場所を
指していれば、その規約を全文読む。

- 指していなければ、文言規約は無いものとして扱い、基礎の原則だけで照合する。規約らしい
  ファイルを名前で探さない。置き場所と名前はリポジトリごとに違い、探して見つけた文書が規約
  として合意されたものかは判断できない

## 3. 画面単位で照合する

変えた文字列だけでなく、それが出る**画面の文言をすべて**集めてから照合する。

1. 変えた文字列の表示元から、それを含む画面 (同時に表示される範囲) のコンポーネントを辿る
2. その画面に出る文言を、見出し・ボタン・本文・注記の区別を付けて列挙する。条件分岐で同時に
   出ないものは、出る組み合わせごとに分けて扱う
3. 基礎の原則と規約の規則を、判定の単位で 2 つに分けて当てる
   - **文字列単位** — 字数、語彙、呼び方、表記、ボタンの名前、エラーの型、読み上げ名。
     1 つずつ判定する
   - **画面単位** — 同じ物の呼び名の揃い、同じ内容 (留保・注意・前提) の繰り返し、見出しや
     ボタンが言ったことの本文での言い直し、1 画面に置く情報の量。上の 2 の列挙全体で判定する

文字列単位の規則は機械でも測れるので守られやすく、画面単位の規則は列挙しない限り見えない。
画面単位の判定を飛ばして文字列単位だけで「規約に沿っている」と判断しない。

対話の場でサブエージェントを起動できるときは、画面の文言だけ (実装・チケット・意図は渡さない)
を読ませ、何が起きている画面か・次に何をするかを答えさせて、意図と突き合わせてもよい。書いた
本人は意図を知っているので、文言から意図が読めるかを自分では判定しにくい。

直す・指摘する対象は、差分が持ち込んだ違反と、差分で悪化した違反 (同じ留保の回数が増えた
など) に限る。差分より前からある違反は直さず、1 件 1 行で残す。置き場所は、実装の工程では
チケットへの報告のスコープ外の気づき、修正の工程では報告の末尾、レビューの工程ではこの文書の
6 に定める 1 行。既存の違反まで直すと、差分がチケットの範囲を超えて広がる。
ただし、チケット (依頼) の目的が既存の文言の改善なら、その範囲の既存の違反は直す・指摘する
対象に含む。そのときは既存の違反を直すことがチケットの範囲そのものになる。

## 4. 事実に反する文言を直すとき

文言が事実と食い違っていると分かったら、条件節や注記を足す前に、次の順に試す。

1. **置き換える** — 断定を、条件を付けなくても成り立つ文に書き換える。状態によって事実が
   変わるなら、文を足すのではなく状態ごとに出す文を分ける
2. **消す** — その文が無くても利用者の判断が変わらないなら消す
3. **既存の文に任せる** — 同じ画面に同じ留保が既にあるなら、それに任せて新しく書かない
4. **足す** — 上の 3 つで済まないときだけ条件節や注記を足し、手順 3 を画面全体でやり直す

文言を足さないと伝わらないもの (操作できることが見た目で分からない、確かさが画面の構成から
読めない) は、文言で説明せずに構成の問題として残す。実装の工程ではチケットへの報告のスコープ外の
気づき、修正の工程では報告の末尾、レビューの工程では `[needs-human]` に置く。足した説明は
画面を重くし、構成の問題を隠す。

正確さの誤りは検証できるので必ず直されるが、直し方は足し算に寄る。回りくどさや重複は検証
しにくく指摘されにくいため、足した文は放っておくと消えずに積み重なる。

## 5. 文言を固定したテスト

- 規約に沿って文を消す・言い換えた結果、既存のテストが文言そのものを期待値にしていて落ちる
  なら、そのテストを直してよい。文言の変更が変更の目的であり、テストを通すための書き換えには
  当たらない。直し方は、リポジトリの規約 (`CLAUDE.md` 等) にテストの方針があればそれに従う。
  無ければ新しい文言で固定し直さず、下の項目と同じく伝えるべき事実の検証に書き換える。固定し
  直すと、次に文を削る変更もまた回帰に見える。直したテストと理由は、工程の報告の「自律判断
  した箇所」(修正の工程では報告の表の下の `テスト修正:` の行) に書く
- 文言を消すこと自体が条件で、テストがその文言だけを検証していたなら、テストを消す。
  不在の検証に書き換えない
- 新しくテストを書くときは、条件が文言そのものを求めていない限り、固定の文言ではなく
  伝えるべき事実 (どの状態で何を出し分けるか、表示する値) を検証する。文言を固定した
  テストは、規約に沿って文を削る変更を回帰に見せる

## 6. レビューでの扱い

レビューの工程で照合したときの分類と優先度。

| 見つけたもの | 分類・優先度 |
| --- | --- |
| 文言規約の明文の規則への違反 (画面単位の規則を含む) | `[auto]` P1 (規約違反) |
| 事実に反する文言、基礎の原則の 4 (事実と確かさ) への違反で、食い違いをコード・差分・同じ画面の文言から確かめられたもの | `[auto]` P1。修正案は手順 4 の順で示す |
| 事実と食い違う疑いがあるが、コードから確かめられないもの | `[needs-human]`。確かめる先を書く |
| 基礎の原則のほかの項目への違反 | `[auto]` P2 |
| 正確さを保つと規約に収まらず、何を削るかに仕様の判断が要る | `[needs-human]` |
| 文言では直らない構成の問題 (手順 4 の末尾) | `[needs-human]` |
| 割れる点 (規約との関係) のうち規約が定めていないものの言い回し | 指摘しない |

差分より前からある違反 (手順 3) は指摘に数えず、トップレベルのコメントの末尾に
`- 既存の違反: <画面> — <規則>` の 1 行ずつで示す。

規約の明文の規則と基礎の原則への違反は、スタイルや好みの指摘ではない。割れる点の言い回しの
好みだけがスタイルの指摘に当たる。再レビューでは、修正で文言が増えて画面単位の規則を割ったものを
「修正で新たに混入した問題」として扱う。
