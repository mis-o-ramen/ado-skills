# UI 文言 — 変えた文言を規約と画面で照合する

差分がユーザーに見える文言を足す・変える・消すときに、その差分をプロジェクトの文言規約と
照合する手順。実装・レビュー・修正のどの工程から読んでも同じ手順を使う。

文言の問題は、文字列を 1 つずつ見ても見つからない。同じ留保の繰り返しや、見出しとボタンの
言い直しは、同じ画面に並ぶ文言をまとめて見たときにだけ現れる。

## 1. 文言の変更を見つける

**ユーザーに見える文言**は、画面・通知・メールとして利用者に表示される文字列を指す。

- 入る: コンポーネントやテンプレートのテキスト、文言リソース・翻訳ファイル、文面を組み立てる
  関数の戻り値、利用者に表示されるエラーメッセージ、`aria-label` などの読み上げテキスト
- 入らない: ログ、内部の例外メッセージ、コードコメント、テストの中の文字列

差分の追加・削除行にある文字列リテラルとテキストを拾い、表示に届くかを参照元で確かめる。
届くものが 1 つでもあれば、この手順の 2 以降を通す。無ければここで終わる。

## 2. 文言規約を読む

リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` が文言規約の場所を
指していれば、その規約を全文読む。

- 指していなければ、文言規約は無いものとして扱う。規約らしいファイルを名前で探さない。
  置き場所と名前はリポジトリごとに違い、探して見つけた文書が規約として合意されたものかは
  判断できない
- 規約が無いときも、手順 4 は適用する。直し方の順序であって、文体の規則ではないため

## 3. 画面単位で照合する

変えた文字列だけでなく、それが出る**画面の文言をすべて**集めてから照合する。

1. 変えた文字列の表示元から、それを含む画面 (同時に表示される範囲) のコンポーネントを辿る
2. その画面に出る文言を、見出し・ボタン・本文・注記の区別を付けて列挙する。条件分岐で同時に
   出ないものは、出る組み合わせごとに分けて扱う
3. 規約の規則を、判定の単位で 2 つに分けて当てる
   - **文字列単位** — 字数、語彙、表記の揺れ。1 つずつ判定する
   - **画面単位** — 同じ内容 (留保・注意・前提) の繰り返し、見出しやボタンが言ったことの
     本文での言い直し、1 画面に置く情報の量。手順 2 の列挙全体で判定する

文字列単位の規則は機械でも測れるので守られやすく、画面単位の規則は列挙しない限り見えない。
画面単位の判定を飛ばして文字列単位だけで「規約に沿っている」と判断しない。

直す・指摘する対象は、差分が持ち込んだ違反と、差分で悪化した違反 (同じ留保の回数が増えた
など) に限る。差分より前からある違反は直さず、1 件 1 行で残す。置き場所は、実装の工程では
チケットへの報告のスコープ外の気づき、修正の工程では報告の末尾、レビューの工程では手順 6 の
1 行。既存の違反まで直すと、差分がチケットの範囲を超えて広がる。
ただし、チケット (依頼) の目的が既存の文言の改善なら、その範囲の既存の違反は直す・指摘する
対象に含む。そのときは既存の違反を直すことがチケットの範囲そのものになる。

## 4. 事実に反する文言を直すとき

文言が事実と食い違っていると分かったら、条件節や注記を足す前に、次の順に試す。

1. **置き換える** — 断定を、条件を付けなくても成り立つ文に書き換える。状態によって事実が
   変わるなら、文を足すのではなく状態ごとに出す文を分ける
2. **消す** — その文が無くても利用者の判断が変わらないなら消す
3. **既存の文に任せる** — 同じ画面に同じ留保が既にあるなら、それに任せて新しく書かない
4. **足す** — 上の 3 つで済まないときだけ条件節や注記を足し、手順 3 を画面全体でやり直す

正確さの誤りは検証できるので必ず直されるが、直し方は足し算に寄る。回りくどさや重複は検証
しにくく指摘されにくいため、足した文は放っておくと消えずに積み重なる。

## 5. 文言を固定したテスト

- 規約に沿って文を消す・言い換えた結果、既存のテストが文言そのものを期待値にしていて落ちる
  なら、そのテストを直してよい。文言の変更が変更の目的であり、テストを通すための書き換えには
  当たらない。直し方は、リポジトリの規約 (`CLAUDE.md` 等) にテストの方針があればそれに従う。
  無ければ新しい文言で固定し直さず、下の項目と同じく伝えるべき事実の検証に書き換える。固定し
  直すと、次に文を削る変更もまた回帰に見える。直したテストと理由は、工程の報告の「自律判断
  した箇所」(修正の工程では報告の表) に書く
- 新しくテストを書くときは、条件が文言そのものを求めていない限り、固定の文言ではなく
  伝えるべき事実 (どの状態で何を出し分けるか、表示する値) を検証する。文言を固定した
  テストは、規約に沿って文を削る変更を回帰に見せる

## 6. レビューでの扱い

レビューの工程で照合したときの分類と優先度。

| 見つけたもの | 分類・優先度 |
| --- | --- |
| 文言規約の明文の規則への違反 (画面単位の規則を含む) | `[auto]` P1 (規約違反) |
| 事実に反する文言 | `[auto]` P1。修正案は手順 4 の順で示す |
| 正確さを保つと規約に収まらず、何を削るかに仕様の判断が要る | `[needs-human]` |
| 規約が無いリポジトリでの言い回しの好み | 指摘しない |

差分より前からある違反 (手順 3) は指摘に数えず、トップレベルのコメントの末尾に
`- 既存の違反: <画面> — <規則>` の 1 行ずつで示す。

規約の明文の規則への違反は、スタイルや好みの指摘ではない。規約が無い言い回しの好みだけが
スタイルの指摘に当たる。再レビューでは、修正で文言が増えて画面単位の規則を割ったものを
「修正で新たに混入した問題」として扱う。
