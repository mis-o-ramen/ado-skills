# 分解 — 親チケットを子チケットに分ける

1 本の PR に収まらない親チケットを、それぞれ 1 本の PR で完結する子チケットに分けて起票
するまでの手順。GitHub でも Azure DevOps でも同じ手順で動く。分解は開発ループの段ではなく
支援工程で、子チケットは実装の工程 (`issue-implement`) の入力になる。着手の承認は子ごとに
人間が行う。

## この工程の入口

入口条件: **1 本の PR に収まらない親チケットがある** (ループの定義は `dev-loop` スキル)。
条件が違う依頼は該当する工程に渡す。

- 親チケットがまだ無く、解決したいことしか無い → `issue-design` (1 本の PR に収まらない
  と分かった時点で、設計の工程が親チケットを起票してここに渡す)
- 子チケットに分かれていて、そのうち 1 つを実装したい → `issue-implement`
- 子チケットの一式をレビューしたい → `issue-review`

チケットレビュー (`issue-review`) が、子チケットの一式に指摘を返してきたときもこの工程で、
「レビュー指摘を受けたら」から入る。

## 能力層

基盤ごとに違う操作は、この本文に「子チケットを起票する」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

**チケット**は GitHub の Issue、Azure DevOps の作業アイテム。**親チケット**は GitHub の
Epic、Azure DevOps のフィーチャー。**受け入れ条件**は Azure DevOps では型ごとのフィールド
(受け入れ基準など) に入る。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| チケットレビュー | 子チケットの下書き一式を `issue-review` にかけ、指摘を反映してから示す | 起票後、ワークフローの指示どおりにチケットレビューを起動する。別の実行が一式をレビューし、親に報告する |
| 起票の承認 | 子チケットの一覧と本文を示し、承認を得てから起票する | 取らない。親に付いた人間の `ai:go` が承認で、子の着手は子ごとに人間が承認する |

チケットの状態 (GitHub のラベル、Azure DevOps の `System.State`) は、GitHub Actions の
ワークフローが指示したときだけ動かす。チャットからの実行では触らない。子チケットの着手の
承認 (GitHub の `ai:go`) はどの文脈でも人間が行い、代行しない。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の上限は次の 2 つ。

- 人間は子チケットを 3〜8 個まとめてレビューする。1 個あたりが長いほどレビューは破綻する。
  **子チケットの本文は、受け入れ条件を除いて 15 行以内** (スコープ外を含む)。受け入れ条件は
  目安 5 件 (手順 3)
- 親へのサマリは折りたたみの外を **合計 20 行以内**

## 手順

### 1. 親チケットと現状を読む

「チケットを読む」で親チケットをコメントまで読む。リポジトリの `CLAUDE.md` / `AGENTS.md` /
`.github/copilot-instructions.md` があれば読み、関連するコードとあわせて現状を掴む。既に
子チケットがあれば、それと重ならないように分ける。

### 2. 分け方を決める

- 各子チケットは、1 本の PR で完結し、単独で検証できる単位にする。曖昧な粒度の
  チケットは曖昧な実装を生む。迷ったら細かく割る
- 子は、親の受け入れ条件を目的と変わる箇所でまとめたグループから作る。子を先に決めて
  条件を後から割り当てると、どの子にも合わない条件が関係の薄い子に押し込まれる
- 子を層 (サーバ・画面・データ) で切らない。利用者が画面で観測する親の条件は、画面から
  処理までを 1 つの子に入れる。層で切ると、どの子にも利用者から観測できる条件が無くなり、
  各子の実装は残りの層を後の子の管轄と読む。層で切るしかないときは、先の子の条件を API
  の呼び出し側から観測できる形で書き、画面を作る子を別に置いて、画面の条件をその子に書く
- 目安は 1 つの親につき 3〜8 個。8 個を超えそうなら、子チケットは作らず、親チケット自体の
  分け方を提案して終える
- 実装順の依存があるなら、どの子がどの子に依存するかを決める。依存の無い子から着手できる
  順に並べる。依存は受け入れ条件の前提から導く (手順 3 の前提の確認)。作業の印象で
  決めた依存は、条件の前提と食い違う

### 3. 子チケットの本文を書く

本文は次の要素だけで書く。各要素をチケットのどこに置くかは「子チケットを起票する」が決める。

- **タイトル** — 動詞で始まる具体的な作業内容
- **背景** — 2 行以内。親のどの部分を担うか
- **作業内容** — 3 行以内。何を変えるか。変わる層 (画面・API・データ) をすべて書く。
  書かれていない層は、実装が後の子の管轄と読む。実装手順は書かない (実装の工程が決める)
- **受け入れ条件** — 1 件 1 行。満たされたかを検証できる文で書く。
  `issue-implement` はこの 1 件ごとにテストを割り振る。1 件には変わる振る舞いを 1 つだけ
  書き、値ごとのテストケースは並べない。どこで観測するか (画面・API・ログ・データ) が
  文から読めるように書く。読めない条件は、実装が作りやすい層だけを作り、残りを兄弟の
  管轄と読む。目安は 5 件。超えたら、別の振る舞いを 1 件に
  束ねたり削ったりせず、その子チケットを手順 2 で分け直す
- **スコープ外** — 親の範囲のうち、この子でやらず兄弟に回したもの。1 件 1 行で、行き先の
  子を `→ #<番号>` で書く (起票前は仮番号)。子を読むのは実装とレビューで、兄弟に回した
  振る舞いは行き先が書かれていなければ「抜け」に見える。最大 3 行。行き先の無い
  スコープ外は書かない。親の段で決まっていないものは「確認してほしいこと」に回す
- **依存** — あれば、先に終わっている必要がある子チケットを 1 行で

親の受け入れ条件が、どれかの子の受け入れ条件に必ず落ちていることを確かめる。どの子にも
落ちない親の条件は、分解の漏れになる。

子の受け入れ条件は、その子のタイトルと作業内容で説明がつき、その子の作業内容の範囲で
満たせるものだけにする。どの子の目的にも合わない親の条件は、関係の薄い子に足さず、新しい
子を作る。子が 8 個を超えるなら手順 2 のとおり親の分け方を提案する。起票の前に、子ごとに
「タイトルと作業内容だけを読んで、各条件がなぜあるか説明できるか」を確かめ、説明できない
条件は正しい子へ移す。

続けて、子の受け入れ条件ごとに**前提の出どころ**を確かめる。条件が前提にする機能・データ・
画面・API を挙げ、それぞれが次のどちらで用意されるかを言う。

- **既にある** — ファイルを開いて確かめた `path`。確かめずに「あるはず」としない
- **依存する子が用意する** — その子の受け入れ条件の番号。その子を「依存」に書く

画面は前提の中でいちばん落ちやすい。サーバ側を用意する子を先に決めると、画面は「後の子が
作るはず」のまま、どの子の作業内容にも書かれない。画面で観測する条件は、その画面を作ると
作業内容に書いた子を名指しできなければ、出どころの無い前提として扱う。

どちらでも言えない前提は、存在しない機能を前提にしている。分解の漏れとして、それを用意する
子を足すか、親の段で決まっていないものとして「確認してほしいこと」に回す。後の子が
用意するものを前提にした条件は、その子より先には検証できない。前提をすべて用意できる
最初の子 (多くは後の子) に移す。

依存し合う子どうしの**つなぎ目**を決める。先に入る子は、後の子がまだ入っていない状態で
リリースされる。その状態で利用者に何が見え、データがどう残るかを、先に入る子の受け入れ
条件にする。書かなければ、先に入る子の実装は後の子を前提にした推測で埋まるか、実装の
工程で止まる。

スコープ外と受け入れ条件が兄弟の間で対になっていることを確かめる。ある子のスコープ外に
`→ #n` と書いた項目は、#n の受け入れ条件に実在する。どの子のスコープ外にも受け入れ条件にも
無い親の範囲は、分解の漏れになる。

最後に、依存を実装順に並べて確かめる。依存が循環していないこと、どの子も自分より後の
子に依存していないこと、各子の完了時点で、その子の受け入れ条件がすべて検証できること。
崩れていれば、条件を移すか子の切り方を変えて直す。依存の向きを逆に書き換えて辻褄を
合わせない。

### 4. レビューにかけ、起票する

チャットでは、承認を求める前に、親と子の下書き一式を `issue-review` にかける。直し先を
兄弟・分け直しとした指摘は下の「レビュー指摘を受けたら」で、その子とした指摘は手順 3 に
戻って反映し、P1 が無くなるまで一式でかけ直す。承認を求めるときは、残った P2 と、
レビューで直したことを 1 件 1 行で添える。

承認の扱いは「実行文脈による違い」の表のとおり。「子チケットを起票する」で、依存される
側から順に起票する。依存は起票した子チケットの番号で書く。

### 5. 親にサマリを残す

「チケットにコメントする」で親チケットに次を残す。書式の制約 (表が使えるか) は能力層に
従う。

- **一覧** — 1 子チケット 1 行。実装順・子チケットへの参照・概要 1 文
- **前提** — 分解にあたって置いた判断。最大 3 件、1 件 1 行。自明な前提は書かない
- **前提の出どころ** — 折りたたみに畳む。子の受け入れ条件ごとに `条件 — 前提 — path か
  子の条件番号` を 1 行。レビューで依存を問われたときに引く
- **確認してほしいこと** — 最大 3 件、1 件 1 行 (粒度・抜け漏れ・優先順位)

チャットでは、同じ内容を会話でも返す。

## レビュー指摘を受けたら

チケットレビュー (`issue-review`) が、子チケットの一式に指摘を返してきたときの手順。
起票前の下書きにも、起票済みの子チケットにも使う。GitHub Actions では、親のコメントに
残ったいちばん新しいチケットレビューの報告が入力になる。

1. 「親チケットを読む」で親を、「子チケットを一覧する」で子をすべて読み直す。起票前なら
   手元の下書き一式を使う。紐づく PR がある子は着手済みで、条件の移し先にも移し元にも
   しない。着手済みの子で埋まらない穴は、未着手の子か、新しい子で埋める
2. 指摘ごとに、手順 2〜3 の分け方の規則で直す
   - 兄弟 — 条件を行き先の子に移す。移した元の子にはスコープ外の行 (`→ #n`) を足し、
     行き先の子の依存・前提の出どころを直す
   - 分け直し — 子を足す・統合する・境界を引き直す。親の受け入れ条件のグループから
     作り直し、変わった子の本文をすべて書き直す
   - その子 — 手順 3 の規則で、その子の本文を直す。既存コードに当てて仕様を詰め直す必要が
     ある穴は直さず、設計の工程 (`issue-design`) に回すものとして報告に残す
   - 親の受け入れ条件そのものが欠けている・矛盾している — 分解では直さない。設計の工程
     (`issue-design`) に戻す
3. 手順 3 の確かめ (条件の所属、前提の出どころ、つなぎ目、スコープ外と受け入れ条件の対、
   実装順) を、変わった子だけでなく一式でやり直す
4. 変わった子の一覧と本文を示し、承認を得る。受け入れ条件の移動・追加・削除は、1 行でも
   承認の対象になる (承認の扱いは「実行文脈による違い」の表のとおり)
5. 起票済みの子は「チケットを書き換える」で、承認を得た本文の全文を書き直す。新しい子は
   「子チケットを起票する」で起票する。親に「チケットにコメントする」で、変わった子と
   移した条件を 1 件 1 行で残す
6. 一式を `issue-review` にかけ直す (GitHub Actions ではワークフローの指示どおりに起動する)

報告は 1 回にまとめる。指摘ごとに `指摘 — 直し先 — 対応` を 1 行で書く。

## やらないこと

- ファイルの作成・編集
- 子チケットの着手の承認の代行 (GitHub の `ai:go` の付与)
- 親チケットの本文の書き換え (親の条件を直すときは設計の工程に戻す)
- 着手済みの子チケット (紐づく PR がある) の受け入れ条件の変更
- 行き先の無いスコープ外、行き先の子の受け入れ条件に無いスコープ外の記述
- チャットで、人間の承認を得ていない起票
- 子チケットの本文への実装手順・クラス名・関数名の記述
- チケットの状態の変更 (ワークフローの指示があるときを除く)
