# 分解 — 親チケットを子チケットに分ける

1 本の PR に収まらない親チケットを、それぞれ 1 本の PR で完結する子チケットに分けて起票
するまでの手順。GitHub でも Azure DevOps でも同じ手順で動く。分解は開発ループの段ではなく
支援工程で、着手の承認は子ごとに人間が行う。

分解が作るのは**骨組みの子チケット**で、受け入れ条件を持たない。子の受け入れ条件は、着手の
直前に設計の工程 (`issue-design` の「子チケットを詳細化する」) が、その時点のコードに当てて
詰める。分解の段で全部の子の細部を詰めると、まだ着手しない子の細部が先の子の実装で覆り、
人間は細部の詰まった子を何個もまとめて読むことになる。分解が決めるのは、親の成果をどの子が
担うかと、子どうしの境界と順序だけ。

## この工程の入口

入口条件: **1 本の PR に収まらない親チケットがある** (ループの定義は `dev-loop` スキル)。
条件が違う依頼は該当する工程に渡す。

- 親チケットがまだ無く、解決したいことしか無い → `issue-design` (1 本の PR に収まらない
  と分かった時点で、設計の工程が親チケットを起票してここに渡す)
- 親に成果が無い (受け入れ条件だけで書かれている) → `issue-design` で親の成果を書き直して
  から戻る。受け入れ条件の束から子を作ると、子は目的ではなく条件の見た目で分かれる
- 子チケットに分かれていて、そのうち 1 つに着手したい → 骨組みなら `issue-design` の
  「子チケットを詳細化する」、受け入れ条件があれば `issue-implement`
- 子チケットの一式をレビューしたい → `issue-review`

チケットレビュー (`issue-review`) が、子チケットの一式に指摘を返してきたときもこの工程で、
「レビュー指摘を受けたら」から入る。

## 能力層

基盤ごとに違う操作は、この本文に「子チケットを起票する」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

**チケット**は GitHub の Issue、Azure DevOps の作業アイテム。**親チケット**は GitHub の
Epic、Azure DevOps のフィーチャー。**成果**は親チケットの本文にある、利用者から見て何が
できるようになるかの一覧で、上からの番号で指す。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| チケットレビュー | 子チケットの下書き一式を、`issue-review` の「Subagent でかける」で回してから示す。起票後、最後の報告を「チケットにコメントする」で親に残す (先頭行は `issue-review` の手順 5 の報告の行) | 同じく Subagent で回してから起票し、最後の報告をワークフローの指示どおりに親に残す |
| 起票の承認 | 子チケットの一覧と本文を示し、承認を得てから起票する | 取らない。親に付いた人間の `ai:go` が承認で、子の詳細化と着手は子ごとに人間が承認する |

チケットの状態 (GitHub の状態ラベル `ai:*`、Azure DevOps の `System.State`) は、GitHub
Actions のワークフローが指示したときだけ動かす。チャットからの実行では触らない。種別の
ラベル (`type:*` / `from:*`) は状態ではなく、起票の一部として付けてよい。子チケットの
承認 (GitHub の `ai:go`) はどの文脈でも人間が行い、代行しない。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の上限は次の 2 つ。

- 人間は子チケットを 3〜8 個まとめてレビューする。1 個あたりが長いほどレビューは破綻する。
  **子チケットの本文は 15 行以内** (スコープ外を含む)
- 親へのサマリは折りたたみの外を **合計 20 行以内**

## 手順

### 1. 親チケットと現状を読む

「チケットを読む」で親チケットをコメントまで読む。背景・目的と成果を、分解の基準として
先に掴む。リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` が
あれば読み、成果ごとに、関連するコードがどこにあるかを掴む。既に子チケットがあれば、
それと重ならないように分ける。

### 2. 分け方を決める

- 子は親の成果から作る。成果 1 つを 1 つの子にするのが基本で、1 本の PR に収まらない成果は
  その成果の中で分ける。複数の成果を 1 つの子にするのは、同じ箇所の変更で一緒に満たせる
  ときだけ
- 各子は、それだけ入れても成果の一部が利用者に届く単位にする。子を層 (サーバ・画面・
  データ) で切らない。利用者が画面で観測する成果は、画面から処理までを 1 つの子に入れる。
  層で切ると、どの子にも利用者から観測できる成果が無くなり、各子の実装は残りの層を後の子の
  管轄と読む。層で切るしかないときは、先の子の成果を API の呼び出し側から観測できる形で
  書き、画面を作る子を別に置く
- 目安は 1 つの親につき 3〜8 個。8 個を超えそうなら、子チケットは作らず、親チケット自体の
  分け方を提案して終える
- 実装順の依存があるなら、どの子がどの子に依存するかを決める。依存の無い子から着手できる
  順に並べる。依存は成果と作業内容の前提から導く (手順 3 の前提の確かめ)

### 3. 子チケットの本文を書く

<!-- 骨組みの要素は issue-design の「子チケットを詳細化する」が読む。変えるときは両方を直す -->

本文は次の要素だけで書く。各要素をチケットのどこに置くかは「子チケットを起票する」が決める。
受け入れ条件は書かない。

- **タイトル** — この子で解決すること。実現手段をタイトルにしない
- **背景** — 2 行以内。親のどの成果 (番号) を担うか
- **成果** — この子が入ったとき、利用者 (API なら呼び出し側) から見て何ができるように
  なるか。1 件 1 行、最大 3 件。どの画面で何を押すと何が表示されるかは書かない (詳細化で
  決める)
- **作業内容** — 3 行以内。何を変えるか。変わる層 (画面・API・データ) をすべて書く。
  書かれていない層は、実装が後の子の管轄と読む。実装手順は書かない
- **スコープ外** — 親の範囲のうち、この子でやらず兄弟に回したもの。1 件 1 行で、行き先の
  子を `→ #<番号>` で書く (起票前は仮番号)。最大 3 行。行き先の無いスコープ外は書かない。
  親の段で決まっていないものは「確認してほしいこと」に回す
- **依存** — あれば、先に終わっている必要がある子チケットを 1 行で

書いたら、次を一式で確かめる。崩れていれば、成果を移すか子の切り方を変えて直す。依存の
向きを逆に書き換えて辻褄を合わせない。

- **成果の被覆** — 親の成果 1 件ごとに、それを担う子の成果がある。どの子にも無い親の成果は
  分解の漏れ。逆に、子の成果 1 件ごとに、それが担う親の成果を番号で言える。言えない子の
  成果は親の目的から外れているので、削る。親に足りない成果だと考えるなら「確認してほしい
  こと」に回す
- **所属** — 子の成果は、その子のタイトルと作業内容で説明がつき、その子の作業内容の範囲で
  満たせる。どの子にも合わない親の成果は、関係の薄い子に足さず、新しい子を作る
- **前提の出どころ** — 子の成果が前提にする機能・データ・画面・API が、既にある (ファイルを
  開いて確かめた `path`) か、依存する子の作業内容で用意されるか。画面は前提の中でいちばん
  落ちやすい。画面で観測する成果は、その画面を作ると作業内容に書いた子を名指しできなければ、
  出どころの無い前提として扱う。どちらでも言えない前提は、それを用意する子を足すか、
  「確認してほしいこと」に回す
- **境界** — ある子のスコープ外に `→ #n` と書いた項目は、#n の成果か作業内容に実在する。
  どの子のスコープ外にも成果にも無い親の範囲は、分解の漏れ
- **実装順** — 依存が循環していない。どの子も自分より後の子に依存していない

### 4. レビューにかけ、起票する

承認を求める前 (GitHub Actions では起票の前) に、子の下書き一式を `issue-review` の
「Subagent でかける」で回す。対象は子の下書き一式、親は親のチケット番号、手順 3 で読む記録は
親のコメント (前回までの報告と対応の記録)。指摘は下の「レビュー指摘を受けたら」で反映する。
下書きへの指摘なので、起票済みの子の書き直しと親へのコメントはしない。最後の報告は、
起票の後で「実行文脈による違い」の表のとおり親に残す。承認を求めるときは、
レビューの判定と、直したこと、残った P1 と P2 を 1 件 1 行で添える。

承認の扱いは「実行文脈による違い」の表のとおり。「子チケットを起票する」で、依存される
側から順に起票する。依存は起票した子チケットの番号で書く。

### 5. 親にサマリを残す

「チケットにコメントする」で親チケットに次を残す。書式の制約 (表が使えるか) は能力層に
従う。

- **一覧** — 1 子チケット 1 行。実装順・子チケットへの参照・担う親の成果の番号
- **前提** — 分解にあたって置いた判断。最大 3 件、1 件 1 行。自明な前提は書かない
- **前提の出どころ** — 折りたたみに畳む。子の成果ごとに `成果 — 前提 — path か子の番号` を
  1 行。レビューで依存を問われたときに引く
- **確認してほしいこと** — 最大 3 件、1 件 1 行 (粒度・抜け漏れ・優先順位)

次の一手は「依存の無い子から、着手する子を詳細化する (`issue-design`)」。手順 4 のレビューで
P1 が残ったなら、次の一手は残った P1 を人間が決めること。チャットでは、同じ内容を会話でも
返す。

## レビュー指摘を受けたら

チケットレビュー (`issue-review`) が、子チケットの一式に指摘を返してきたときの手順。
子を詳細化していた設計の工程が、分け直しか兄弟への移動を回してきたときも、それを指摘として
同じ手順で受ける。起票前の下書きにも、起票済みの子チケットにも使う。起票済みの一式なら、親のコメントに
残ったいちばん新しいチケットレビューの報告が入力になる。チャットで、別のセッションの
レビューを受けるときも、指摘を貼り直してもらわずにここから読む。

1. 「親チケットを読む」で親を、「子チケットを一覧する」で子をすべて読み直す。起票前なら
   手元の下書き一式を使う。受け入れ条件のある子 (詳細化済み) と紐づく PR がある子 (着手
   済み) は、成果の移し先にも移し元にもしない。それで埋まらない穴は、骨組みの子か、
   新しい子で埋める
2. 指摘ごとに、手順 2〜3 の分け方の規則で直す
   - 兄弟 — 成果を行き先の子に移す。移した元の子にはスコープ外の行 (`→ #n`) を足し、
     行き先の子の依存・前提の出どころを直す
   - 分け直し — 子を足す・統合する・境界を引き直す。親の成果から作り直し、変わった子の
     本文をすべて書き直す
   - その子 — 骨組みの子なら、手順 3 の規則でその子の本文を直す。詳細化済みの子の受け入れ
     条件への指摘はこの工程では直さない (`issue-design` が受け取る)
   - 親の成果そのものが欠けている・矛盾している — 分解では直さない。設計の工程
     (`issue-design`) に戻す
   - 見送る — 指摘の前提が一式と合わない (指摘された成果が既に別の子にある、前提が
     `path` に既にある)。一式の成果の番号か `path` を根拠に示す。根拠を示せないなら見送らない
3. 手順 3 の確かめを、変わった子だけでなく一式でやり直す
4. 一式を手順 4 と同じく `issue-review` の「Subagent でかける」で回す。その周回の中で受けた
   指摘を反映しているときは、ここで回し直さない (周回は「Subagent でかける」が数える)
5. 変わった子の一覧と本文を示し、承認を得る。成果の移動・追加・削除は、1 行でも承認の
   対象になる (承認の扱いは「実行文脈による違い」の表のとおり)
6. 起票済みの子は「チケットを書き換える」で、承認を得た本文の全文を書き直す。新しい子は
   「子チケットを起票する」で起票する。親に「チケットにコメントする」で、先頭行を
   `チケットレビューへの対応 (ラウンド N)` (N は受けた報告のラウンド) にして、変わった子と
   移した成果、見送った指摘とその根拠を 1 件 1 行で残す。次のチケットレビューは、見送りの
   根拠をここから引いて、同じ指摘を繰り返すかを決める。4 のレビューの最後の報告は、
   「実行文脈による違い」の表のとおり親に残す

報告は 1 回にまとめる。指摘ごとに `指摘 — 直し先 — 対応` を 1 行で書く。

## やらないこと

- リポジトリのファイルの作成・編集 (レビューにかける下書きの書き出しを除く)
- 子チケットの受け入れ条件の記述 (着手の直前に `issue-design` が詳細化する)
- 子チケットの承認の代行 (GitHub の `ai:go` の付与)
- 親チケットの本文の書き換え (親の成果を直すときは設計の工程に戻す)
- 詳細化済み・着手済みの子チケットの成果と受け入れ条件の変更
- 親の成果で説明のつかない成果の、子への記述
- 行き先の無いスコープ外、行き先の子に無いスコープ外の記述
- チャットで、人間の承認を得ていない起票
- 子チケットの本文への実装手順・クラス名・関数名の記述
- チケットの状態の変更 (ワークフローの指示があるときを除く)
