# 設計 — アイデアをチケットに落とす

人間の粗いアイデアを起点に、対話と調査を経て、実装に着手できるチケットを作るまでの
手順。GitHub でも Azure DevOps でも同じ手順で動く。出力は実装の工程 (`issue-implement`)
の入力になる。あちらが「受け入れ条件が空なら止まる」「推測で実装しない」と定めている
以上、ここで作るチケットは、実装する人が質問せずにテストと実装を書けるところまで
埋まっていなければ意味がない。

## この工程の入口

入口条件: **解決したいことはあるが、受け入れ条件の埋まったチケットが無い** (ループの
定義は `dev-loop` スキル)。条件が違う依頼は該当する工程に渡す。

- 受け入れ条件の埋まったチケットが既にあり、実装を求められている → `issue-implement`
- PR のレビュー → レビューの工程、PR への指摘の対応 → `pr-fix`
- 既にある親チケットを子チケットに分けたい → `issue-plan`
- 着手前のチケットを、親・兄弟とまとめてレビューしたい → `issue-review`
- 仕様を決める前に調べてほしいだけ → `issue-research`

起点はチャットの依頼でも、粗く起票済みのチケットでもよい。チケットが起点なら「チケットを
読む」でコメントまで読んでから始める。過去の実行で出した質問への回答はコメントに残って
いる。起票前の設計メモにレビューの指摘が付いて戻ってきたときや、チケットレビュー
(`issue-review`) が直し先をそのチケットか親とした指摘を返してきたときもこの工程で、
「レビュー指摘を受けたら」から入る。

## 能力層

基盤ごとに違う操作は、この本文に「チケットを起票する」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

用語も能力層に合わせて読み替える。**チケット**は GitHub の Issue、Azure DevOps の
作業アイテム。**受け入れ条件**は Azure DevOps では型ごとのフィールド (受け入れ基準など)
に入る。

## 実行文脈による違い

手順は同じで、人間への確認の届け方と設計メモの置き場所だけが違う。

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 質問・方針の選択肢 | 会話でそのまま確認する | チケットのコメントに 1 つにまとめて残し、ワークフローの指示どおりに止まる |
| 設計メモ | ファイルに置く。置き場所は依頼者の指定に従い、指定が無ければ作業ディレクトリに置いてパスを報告する | 本文はチケットに直接書き、自分で決めたことと検討記録は報告のコメントの折りたたみに置く |
| 本文の承認 | 設計メモを見せて承認を得てから起票する | 取らない。チケットの編集は可逆で、実装の着手は人間の `ai:go` が承認する |

チケットの状態 (GitHub のラベル、Azure DevOps の `System.State`) は、GitHub Actions の
ワークフローが指示したときだけ動かす。チャットからの実行では触らない。実装の着手の承認
(GitHub の `ai:go`) はどの文脈でも人間が行い、代行しない。

## 出力規約

`output-contract` スキルを前提とし、方針の選択肢の形式は `consult-response` スキルがあれば
それに従う。この工程固有の上限は次の 4 つ。

- 人間への質問は 1 回にまとめて最大 5 件、1 件 1 行。小出しにしない。溢れた分は、覆すと
  手戻りが大きいものを先にして次の往復に回す
- 仕様を決める質問には推奨と根拠 (`path:line` かチケット番号) を付ける。選択肢だけを
  並べて「どうしますか」と返さない。推奨を出せないときは、何が分からないから出せないのかを
  書く。設計の工程は設計相談を受けている場で、判断材料はここまでの調査で自分が持っている
- 方針の選択肢は最大 3 案。1 案 1 行に帰結を 1 句添え、推奨に印をつける
- 設計判断としてチケットに書くのは最大 3 件。**覆すと手戻りになるものだけ**

受け入れ条件は 1 チケット **8 件が目安**。これは書き方の上限ではなく、分割を判断する合図に
使う。超えたときにしてよいのは、手順 5 の粒度の見直しとチケットの分割だけ。関係の無い
条件を 1 件に束ねる、境界・異常系を削る、で 8 件に収めてはいけない。

## 自分で決めることと、人間に聞くこと

チケットに書かれなかった仕様は消えない。実装の工程で止まるか、実装者の推測で埋まるか、
レビューで「未定義」の指摘になる。どれも設計の工程で埋めるより高くつく。だから埋める。
誰が埋めるかは次の線で分ける。

- **自分で決める** — 手順 1 の「委ねられていること」に入るもの。既存コードの振る舞いに
  揃える、同種の既存機能に合わせる、で決まるものが大半を占める。決めたことは根拠を添えて
  手順 7 で示し、人間はそこで覆せる
- **人間に聞く** — 「解決したいこと」「決まっていること」に触れるもの、委ねられた範囲の
  外にあるもの、コードからは決まらない業務上の判断 (誰に何を許すか、データをいつ消すか)。
  出力規約の形で、推奨を付けて聞く

決めていない事項を見つけたら、聞く前にこの線で分ける。委ねられた範囲のものを質問にすると、
調査の仕事が人間に移るだけになる。

## 手順

### 1. 解決したいことを聞き取る

アイデアは「何を作るか」の形で来ることが多い。実装に落とす前に「何を解決するか」に
引き直す。作るものが同じでも、解決したいことが違えば受け入れ条件が変わる。

次の 3 つを依頼者との対話で確認する。

- **何を解決するか** — 今、誰が、何に困っているか。今はどう凌いでいるか
- **決まっていること** — 依頼者の中で確定していて、覆してはいけないこと
- **委ねられていること** — こちらの調査と提案で決めてよいこと

答えが本文・コメントから読み取れるなら聞かない。曖昧な点だけを質問にして、まとめて
1 往復で確認する。解決したいことが確認できないまま先へ進まない。作り方の議論は
解決したいことが定まってからで、逆順にすると選択肢の比較軸が作れない。

「委ねられていること」は後の手順で自分が決めてよい範囲の線になる。依頼者が明言しない
ときは「既存の振る舞いに揃える範囲はこちらで決め、承認時に一覧で示す」と伝えて確認する。

### 2. 既存を調べる

コードベースの読解を主にする。ネットワークが社内に閉じている場合、外部の検索や取得は
使えない。到達できない情報源を前提にした計画を立てない。

- リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
  規約と構成を把握する
- 同じ課題を扱ったチケットが既に無いか「チケットを探す」で探す。重複や過去の見送りが
  見つかれば、それ自体が判断材料になる
- 実現方法の候補を、既存コードのどこに乗るかまで特定する。ファイルを開かずに挙げた
  候補は選択肢ではなく想像で、選ばれた後で覆る

### 3. 方針の選択肢を出し、人間が選ぶ

調査で得た選択肢を最大 3 案、1 案 1 行の「案 — 帰結を 1 句」で並べ、推奨に印をつける。
覆すと手戻りになる懸念があれば 1 件 1 行で添える。

**選ぶのは人間。ここで止まり、選択を待つ。** 実質 1 案しかないときは選択肢の形をやめ、
その方針と根拠を示して異議がないかだけ確認する。

方針と一緒に、クラス名・関数名・画面文言といった実装の細部を出さない。それは実装の
工程の裁量で、ここで固定すると判断材料が実装案の中に埋もれる。

### 4. 既存コードに当てて仕様を詰める

手順 3 の比較は「どこに乗るか」までしか見ていない。選んだ方針を、それが乗る既存コードに
当てて、決めていないことを洗い出す。ここを飛ばした本文は、実装やレビューで初めて読まれる
コードとぶつかって覆る。

1. 変更が入る箇所と、同じデータ・画面・API・設定を使う既存の利用箇所を特定する。
   参照元を辿り、ファイルを開いて読む。利用箇所の一覧は検討記録に `path` で残す
2. 次の観点ごとに、この変更で何が起きるかを決める

| 観点 | 問うこと |
| --- | --- |
| 入力と境界 | 空・0 件・上限・不正値・重複のとき何が起きるか |
| 状態 | 途中の状態、取り消し・やり直し、二重実行のとき何が起きるか |
| 失敗 | 依存先の失敗・途中までの成功・タイムアウトで、利用者に何が見え、データがどう残るか |
| 並行 | 同じ対象への同時操作で何が起きるか |
| データ | 既存データの扱い (移行・初期値)、削除と保持 |
| 権限 | 誰が、誰の何に対してできるか |
| 既存への影響 | 1 で特定した既存の利用箇所の振る舞いが変わるか。互換性 |
| 規模 | 件数・サイズ・頻度が既存の想定を超えるか |
| 運用 | 設定、ログ、切り戻し |

   利用者に見える画面を新しく作る・変えるなら、`impeccable` スキルがあれば、表を当てる
   前にそのディレクトリの `reference/shape.md` を直接開いて読む。ディレクトリは
   `.claude/skills/`・`.github/skills/`・`.agents/skills/` か、ホームの `~/.claude/skills/`・
   `~/.copilot/skills/`・`~/.agents/skills/` の下の `impeccable/` にある (実行文脈が場所を
   示していればそれに従う)。スキルとしては呼び出さず、
   `SKILL.md` も読まない (読むと実行ファイルの起動や聞き取りの手順が始まる)。`shape.md`
   から先の参照 (`new-work.md` など) は辿らない。足す観点は次の 4 つで、結論は上の表と
   同じく検討記録に残す。ここに挙げたのは要約で、参照を読む代わりにはならない
   - 画面の状態と値の範囲 — 初回・空・読み込み中・エラー・権限・溢れ、内容の最小・典型・最大
   - 操作の流れとフィードバック — 操作の結果が利用者に見えるか、取り消し・遷移
   - 端末幅 — 狭い幅で読めて操作できるか
   - アクセシビリティ — キーボードと支援技術で操作でき、読めるか

   画面の構成・配置・見た目 (色・フォント・余白) は実装の工程の裁量で、ここで決めない。
   `shape.md` の聞き取り・ブリーフ・確認して止まる手順には従わず、観点の中身だけを使う。
   PRODUCT.md・DESIGN.md は作らない。聞くかどうかは「自分で決めることと、人間に聞くこと」の
   線で決め、聞くときはこの工程の出力規約の形で出す。
   スキルが無ければ上の表の観点だけで進める
3. 観点ごとの結論を検討記録に 1 行で残す。形は `観点 — 結論 — 根拠 — 反映先`
   - 反映先は受け入れ条件の番号、スコープ外、設計判断のどれか。利用者に見える振る舞いを
     決めたなら受け入れ条件にする。決めた振る舞いが本文のどこにも無ければ、実装者には
     決まっていないのと同じ
   - 既存の利用箇所 (別の画面・機能) の振る舞いを受け入れ条件にできるのは、その箇所の
     コードを変えずに、このチケットの変更の結果として成り立つものだけ。利用箇所の側も
     変えないと成り立たないなら、それは別の目的の作業で、反映先はスコープ外 (別チケット)
   - 「該当なし」は、該当しない根拠 (`path:line`) と一緒にだけ書ける。根拠の無い
     該当なしは、検討していないのと区別が付かない
   - 決まらないものは「自分で決めることと、人間に聞くこと」の線で分け、人間に聞くものを
     質問にまとめる

回答を得たら反映し、回答で変わった観点を当て直す。結論の無い観点を残したまま手順 5 に
進まない。

### 5. チケットの本文を書く

本文は次の要素で書く。各要素をチケットのどこ (本文の見出し、型ごとのフィールド) に
置くかは「チケットを起票する」が決める。

- **タイトル** — 解決することを書く。実現手段をタイトルにしない
- **背景・目的** — 手順 1 で確認した「解決したいこと」。実装する人が読むのはチケットだけで、
  この対話は残らない
- **受け入れ条件** — 1 件 1 行、満たされたかを検証できる文で書く。正常系だけでなく、
  手順 4 で決めた境界・異常系の振る舞いも条件にする。`issue-implement` はこの 1 件ごとに
  テストを割り振る。「〜できること」で終わる曖昧な文は割り振れず、そこで実装が止まる
  - 1 件は、このチケットで変わる振る舞いを 1 つ、利用者 (API なら呼び出し側) から
    観測できる形で書く。別の観点・別の箇所の振る舞いを「、」「かつ」「また」で 1 件に
    つながない。束ねた条件は合否を 1 件単位で判定できず、一部だけ満たした実装が通るか
    落ちるかが決まらない
  - どこで観測するか (画面・API・ログ・データ) が文から読めるように書く。「〜を登録
    できる」だけでは、画面から登録できるのか API で登録できるのかが決まらず、実装は
    作りやすい層だけを作る
  - 受け入れ条件はテストケースの一覧ではない。同じ操作に同じ期待を持つ入力の違い (境界値、
    不正値の種類) は値ごとに並べず、振る舞いとして 1 件に書く。どの値で確かめるかは
    実装の工程が決める。書く「上限を超える件数を渡すと、1 件も保存せずに上限を示すエラーを
    返す」。書かない「101 件で〜」「1000 件で〜」「負の数で〜」を別々の条件にする
  - 変わらない振る舞いは条件にしない。手順 4 で、この変更で変わりうると特定した既存の
    利用箇所だけを「〜は変わらない」の条件にする。それ以外の「変わらない」は検討記録に残す
  - 利用者に見える文言が関わる条件は、**利用者が画面から読み取れる事実**と**表示しては
    いけない誤り**を、それが成り立つ状態と一緒に書く。どう直すか (文を足す・消す・置き
    換える、どの箇所に出す、何回出す) は書かない。直し方は、同じ画面に並ぶ文言をまとめて
    見られる実装の工程が `ui-copy` の手順 4 の順で選ぶ。条件が直し方を指定すると、実装と
    レビューはその順を使えず、条件に従って文を足すしかなくなる
  - 文言そのものを書かなくても、「〜という趣旨の文にする」「〜を前提にした文になる」
    「A にも B にも〜を入れる」は直し方を 1 つに固定する。画面文言の記述として扱い、書かない
  - 伝え続けるべき事実があるなら、「この注記は外さない」ではなく「〜が同じ画面から分かる」
    の形で事実の条件にする。文を残すかどうかは直し方で、事実が伝わるかどうかは検証できる
  - 例: 書く「すべての取得を記録した利用者に、取得の記録が足りないと表示しない」「記録して
    いない取得があれば実際の残りが少なくなることが、残日数と同じ画面から分かる」。書かない
    「注記を『記録した取得のほかに…』という趣旨にする」「カード X とカード Y の注記も同じ
    前提の文にする」
- **スコープ外** — 手順 4 で反映先をスコープ外にしたもの、下の「条件がこのチケットに
  属するか」から外れたもの。別チケットにするものはそう書く

受け入れ条件は、次の 2 つを両方満たすものだけをこのチケットに書く。片方でも外れる条件は、
どれほど関連が深く見えても別チケットの条件になる。件数の目安に余裕があることは、入れる
理由にならない。

- **目的で説明がつく** — タイトルと背景・目的だけを読んだ人が、なぜこの条件があるかを
  言える。「マスタを整備する」チケットに、入力フォームの操作性の条件は説明がつかない
- **このチケットで変える範囲で満たせる** — 満たすために変わる箇所が、このチケットの
  変更の範囲に入る。別の画面・機能のコードも変えないと満たせない条件は入れない
- **設計判断** — 手順 3 で人間が選んだ方針と、覆すと手戻りになる決定だけ。最大 3 件

1 つのチケットは、独立してレビューできる 1 本の PR で完了する粒度にする。超えるなら
「親チケットを起票する」で親として起票し、子チケットへの分解は分解の工程 (`issue-plan`)
に渡す。

受け入れ条件が目安の 8 件を超えたら、次の順に進める。

1. 粒度を見直す。テストケースを並べた条件は振る舞いにまとめ、変わりうると特定して
   いない「変わらない」条件は検討記録に移す。まとめてよいのは、同じ操作に同じ期待を持つ
   ものだけ
2. それでも超えるなら、チケットを分ける。片方だけ出しても解決したいことが進む目的の
   単位か、変わる箇所が互いに関係しない領域の単位で切る。親として起票し、ここまでに
   決めた受け入れ条件は親の本文に残して分解の工程に渡す
3. 目的も変わる箇所も 1 つで分けようがないときだけ、8 件を超えたまま 1 チケットにする。
   分けない理由を手順 7 の「自分で決めたこと」に書く。目安の 2 倍 (16 件) を超えるなら、
   分けようがないという判断を疑い、分け方の案を添えて人間に聞く

### 6. 自分でレビューする

依頼者に見せる前に、本文を別の読み手として読み直す。実装する人はチケットだけを読み、
レビューする人は本文とコードを突き合わせる。この二人が出す問いを、ここで出し切る。

- 受け入れ条件 1 件ごとに、満たすために変わる箇所を `path` で言えるか。言えない条件は、
  どこに乗るかがまだ決まっていない。画面で観測する条件なら、画面の `path` まで入って
  いるか。サーバ側の `path` だけなら、画面を誰が作るかが決まっていない
- 受け入れ条件 1 件ごとに、前提にする機能・データ・画面・API が、既にある (`path` で
  確かめた) か、このチケットの変更で用意されるか。どちらでもない前提は存在しない機能を
  前提にしている。このチケットで用意するか、別チケットにして条件から外す
- 受け入れ条件 1 件ごとに、手順 5 の「条件がこのチケットに属するか」の 2 つを満たすか。
  タイトルと背景・目的だけを読んで、各条件がなぜあるかを説明してみる。説明できない条件、
  別の画面・機能の変更が要る条件はスコープ外に移し、別チケットにする
- 受け入れ条件 1 件ごとに、落ちるテストの前提・操作・期待が書けるか。操作か期待が
  2 通り以上になる条件は、別の振る舞いを束ねている。分けて書く
- 受け入れ条件が、値ごとのテストケースや、変わりうると特定していない「変わらない」の
  列挙になっていないか。件数が目安の 8 件を超えていれば手順 5 の順で進めたか
- 本文の語が定義されているか。「適切に」「エラー時は」「必要に応じて」「など」のように、
  実装者に振る舞いを選ばせる語は未定義として扱う
- 文言が関わる条件が、事実ではなく直し方 (足す文、文の趣旨、出す箇所と回数) を指定して
  いないか。指定していれば、その直し方で伝えたかった事実に書き直す
- 条件同士、条件と「決まっていること」、条件とスコープ外が矛盾しないか
- 親があるチケットでは、「親チケットを読む」「子チケットを一覧する」で兄弟を読み、
  受け入れ条件が兄弟の受け入れ条件と重ならないか、スコープ外で兄弟に回した範囲に入って
  いないかを確かめる。文面が矛盾しなくても、兄弟の条件の一部を足していれば重なっている
- 検討記録のすべての観点に結論と根拠があり、反映先が本文に実在するか

見つけた穴は手順 4 に戻って埋める。ここで見つけた穴は自分で埋められるが、レビューや
実装で見つかった穴は人間との往復を増やす。

### 7. 設計メモを示し、承認を得る

設計メモは次の 3 部からなる。置き場所は「実行文脈による違い」の表のとおり。

- **本文** — 手順 5 の要素。起票される内容そのもの
- **自分で決めたこと** — 委ねられた範囲として自分で決めた事項。1 件 1 行、根拠付き
- **検討記録** — 手順 4 の既存の利用箇所と、観点ごとの結論。チケットの本文には入れず、
  レビューの指摘に答えるときに引く

親を持たないチケットも、依頼者が望めば、承認を求める前に `issue-review` にかけられる。
子チケットの一式は、分解の工程が起票前に必ずかける。

本文の承認は「実行文脈による違い」の表のとおり。起票前に固めるのが安い (Azure DevOps の
フィールドは起票後に読み戻して書き直せないことがある。能力層を参照)。承認後の修正指示の
うち、本文の意味が変わらない反映 (誤字、表記の統一、行の並べ替え) はそのまま起票して
よい。受け入れ条件の追加・削除・文言の変更、タイトルの変更、スコープ外の追記は、反映した
本文をもう一度見せて承認を得る。軽微かどうかを自分で決めない。受け入れ条件は実装と
レビューの基準そのものなので、1 行の違いが PR の合否を変える。

### 8. 起票して報告する

「チケットを起票する」で起票する。起点のチケットがあるとき、それを書き換えるか、新しく
起票して起点から参照するかは能力層に従う。

チャットでは、起票したチケットに「チケットにコメントする」で、自分で決めたことと検討記録を
折りたたみに残す (GitHub Actions では報告のコメントに既にある)。設計メモのファイルは
この会話の手元にしか無く、別のセッションのチケットレビューからは引けない。引けない判断は
検討していないのと同じに見え、レビューのたびに同じ穴が指摘される。

報告は起票・更新したチケットへの参照 1 行と、次の一手 1 行 (内容を確認して実装に着手。
親チケットを起票したときは分解に進む) のみ。本文の内容を報告に繰り返さない。

## レビュー指摘を受けたら

設計メモや起票済みで未着手のチケットを別のレビュー (チケットレビュー `issue-review` を
含む) にかけ、その指摘が戻ってきたときの手順。指摘の一覧を
そのまま人間への質問に変換して返さない。指摘に答えるのは、設計した側の仕事になる。

1. 親があるチケットなら、「親チケットを読む」で親を、「子チケットを一覧する」で兄弟を
   読む。指摘ごとに、まずそのチケットの範囲かを判定する。チケットレビュー (`issue-review`)
   が付けた直し先があれば、それを起点にする
   - **兄弟の範囲** — 指摘を埋める振る舞いが、このチケットのスコープ外に行き先として
     書かれているか、兄弟の目的で説明がつく。スコープ外の行か兄弟の条件番号を根拠に示して
     見送る。兄弟にも行き先が無い穴なら、直し先を兄弟として `issue-plan` に回す
   - **境界の誤り** — 埋めると、このチケットの目的が変わるか、兄弟の範囲を跨ぐ。直さずに
     分け直しとして `issue-plan` に回す
   - **このチケットの範囲** — 上のどちらでもない。次の 2 に進む

   「このチケットの範囲」と判定したときは、兄弟の範囲ではない理由を 1 句添える。添えられ
   ないなら判定を誤っている。子チケットに指摘を足していくと、境界は直らずに子が膨らむ
2. このチケットの範囲の指摘ごとに検討記録を引き、次の 2 つに分ける
   - **検討済み** — 記録か本文 (スコープ外・設計判断) に結論と根拠がある。指摘が根拠を
     崩していなければ、根拠を示して見送る。崩していれば検討漏れとして扱う
   - **検討漏れ** — 記録に無いか、根拠が無い。手順 4 と同じくコードを辿って結論を出し、
     「自分で決めることと、人間に聞くこと」の線で分ける
3. 検討漏れは症状として扱う。漏れた観点を本文全体に当て直し、同じ観点の他の漏れも埋める。
   指摘された 1 箇所だけを直すと、次のレビューで同じ観点の指摘が別の箇所から出る。当て
   直して見つかった漏れにも 1 の範囲の判定をかける
4. 設計メモに反映し、手順 6 の自己レビューをやり直す
5. 起票済みのチケットなら、承認を得た本文の全文を「チケットを書き換える」で書き直す。
   子チケットの受け入れ条件を変えたら、兄弟との境界が動いた可能性があるので、一式を
   `issue-review` にかけ直す。チャットでは、別のセッションでかけ直すことを次の一手にする
6. 報告は 1 回にまとめる。指摘ごとに
   `指摘 — 兄弟の範囲 / 境界の誤り / 検討済み / 検討漏れ — 対応` を 1 行で書き、人間に
   聞くものは出力規約の質問の形で末尾に並べる。本文が手順 7 の再提示に当たる変わり方を
   したら、同じ報告の中で承認を求める。起票済みのチケットなら、書き直しを終えた後
   (書き直しが無ければ報告の後) に、人間に聞くものを除いた同じ報告を「チケットに
   コメントする」で親 (親が無ければそのチケット) にも残す。チケットレビューの指摘を受けた
   ときは、先頭行を `チケットレビューへの対応 (ラウンド N)` (N は受けた報告のラウンド) にする。次のチケットレビューは、
   見送りの根拠をここから引く

「設計時点でどう考えていたか」と問われたら、検討記録の該当行を示す。行が無ければ検討漏れと
答え、同じ報告の中で上の 1 から進めた結論を示す。「どうしますか」だけを返さない。

## やらないこと

- 実装・ブランチ作成・PR 作成 (`issue-implement` の領分)
- 実装の着手の承認の代行 (GitHub の `ai:go` の付与)
- チャットで、人間の承認を得ていない起票
- 受け入れ条件が埋まっていないチケットを、実装できる種別 (GitHub の `type:feature` /
  `type:bug`) にすること
- 実装の細部 (クラス名・関数名・画面文言) のチケットへの記述。文言の趣旨・出す箇所・
  足すか消すかの指定も画面文言の記述に含む
- 検証できない受け入れ条件の記述
- 件数を減らすための、関係の無い受け入れ条件の結合・境界や異常系の条件の削除
- テストケースの列挙としての受け入れ条件の記述
- 根拠の無い「該当なし」、結論の無い観点を残したままの本文の提示
- 推奨の無い仕様の質問、委ねられた範囲の事項の質問
- 兄弟の範囲かを確かめずに、レビューの指摘を子チケットの受け入れ条件に足すこと
- チケットの状態の変更 (ワークフローの指示があるときを除く)
- 確認していない影響・利用者像・画面名の記述
