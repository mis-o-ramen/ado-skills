# チケットレビュー — 着手前のチケットをセットで見る

実装に着手する前のチケットを、親と兄弟の子チケットとまとめて 1 つのセットとして読み、
直し先の付いた指摘を返すまでの手順。GitHub でも Azure DevOps でも同じ手順で動く。
チケットレビューは開発ループの段ではなく支援工程で、チケットを直さない。指摘は直し先に
応じて設計の工程 (`issue-design`) か分解の工程 (`issue-plan`) が受け取る。

子チケット 1 つだけを読むレビューは、足りないものをすべてその子に足す方向にしか指摘
できない。兄弟に回した振る舞いも「抜け」に見え、直すたびに子の範囲が兄弟に食い込む。
この工程が単位をセットにするのはそのため。

## この工程の入口

入口条件: **実装に着手していないチケットがあり、着手の前に確かめたい** (ループの定義は
`dev-loop` スキル)。次のどれかで呼ばれる。

- 分解の工程が、起票前の子チケットの下書き一式を示す前 (チャットでは必ず通す)
- 子チケットの受け入れ条件を変えた後。兄弟との境界が動いた可能性がある
- 先の子チケットがマージされた後。残りの子の前提が、実装されたコードとずれていないか
- 親を持たないチケットの起票前に、依頼者がレビューを求めたとき

条件が違う依頼は該当する工程に渡す。

- PR のレビュー → `pr-review`
- 指摘を受けてチケットを直す → 直し先がその子なら `issue-design`、兄弟・分け直しなら
  `issue-plan` (下の「指摘の受け取り手」)
- 着手済みのチケット (紐づく PR がある) の受け入れ条件の不足 → 実装の工程が止まって
  返した不足として `issue-design` に渡す

## 能力層

基盤ごとに違う操作は、この本文に「子チケットを一覧する」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

**チケット**は GitHub の Issue、Azure DevOps の作業アイテム。**親チケット**は GitHub の
Epic、Azure DevOps のフィーチャー。**受け入れ条件**は Azure DevOps では型ごとのフィールド
(受け入れ基準など) に入る。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 起動 | 依頼者か分解の工程が呼ぶ | 親か子に `ai:check` が付いたとき (分解のワークフローが起票後に付ける)、子がクローズされたとき |
| 対象 | 起票前の下書きか、起票済みのチケット | 起票済みのチケットだけ |
| 報告の置き場所 | 起票前の下書きなら会話で返す。起票済みなら「チケットにコメントする」で親に残し、会話でも返す | 「チケットにコメントする」で親 (親が無ければそのチケット) に 1 コメント。ワークフローが指定する行を先頭に置く |

チケットの状態 (GitHub のラベル、Azure DevOps の `System.State`) は動かさない。GitHub
Actions では、報告を読んだワークフローがラベルを付け替える。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の優先度と上限は次のとおり。

| 優先度 | 基準 |
| --- | --- |
| P1 | このまま着手すると実装の工程が止まるか、推測で埋まる。子どうしの重複・矛盾、どの子にも無い親の条件、その子に属さない条件、前提の出どころが無い条件 |
| P2 | 実装は一意に決まるが、読み手を迷わせる。表記の揺れ、束ねられていないが分けたほうが読みやすい条件 |

チケットはそれ自体では何も壊さないので、P0 は使わない。迷ったら低い方に倒す。

- P1 は、子 1 つあたり **5 件まで**。超える子は、指摘を足して直す段階に無い。その子の
  個別の指摘を並べず、「分け直し」を直し先にした 1 件にまとめ、超えた理由 (境界が
  どこで崩れているか) を 1 行で書く
- P2 はセット全体で **3 件まで**。溢れた分は `- その他 P2 N 件` の 1 行だけで示す
- 指摘は 1 件 1 行、`[P1] 観点 — 指摘 — 直し先 — 根拠` の形にする。根拠は
  `path:line`、チケットの条件番号、親の条件番号のどれか

## 手順

### 1. セットを集める

レビューする単位は、親チケットと、その親のすべての子チケット。

1. 起点のチケットを「チケットを読む」でコメントまで読む
2. 「親チケットを読む」で親を読む。親があれば「子チケットを一覧する」で兄弟をすべて集め、
   それぞれ「チケットを読む」で読む。起票前の下書きなら、分解の工程が示した下書き一式を
   そのまま使う
3. 各子について、着手済みか (紐づく PR があるか、マージ済みか) を控える。着手済みの子は
   読むが、直し先にしない (手順 3)
4. 設計の検討記録 (設計メモ) があれば読む。指摘が検討済みかどうかは、受け取り手が
   これを引いて判断する

親があるのに兄弟の一部しか手に入らないときは、レビューを始めずに、足りない子を依頼者に
求める。兄弟が欠けたセットでは、手順 2 の境界を判定できない。

リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
受け入れ条件が前提にするコードは、ファイルを開いて確かめる。

### 2. 観点ごとに確かめる

セット全体の観点を先に見て、子ごとの観点は後に見る。子ごとに見てから全体を見ると、
個々の子の「足りない」がすべてその子への追加として指摘される。

**セット全体**

1. **被覆** — 親の受け入れ条件が、どれか 1 つの子の受け入れ条件に落ちているか。どの子
   にも無い親の条件は漏れ、2 つ以上の子にある条件は重複
2. **境界** — 各子のスコープ外に書かれた項目が、その行き先の兄弟の受け入れ条件として
   実在するか。逆に、子の受け入れ条件が、別の子のスコープ外に「この子でやる」と書かれた
   範囲を越えていないか
3. **つなぎ目** — 依存し合う子どうしで、相手の子がまだ入っていない状態の振る舞いが、
   先に入る側の子の受け入れ条件で決まっているか。決まっていなければ、先に入る子の実装は
   相手を前提にした推測で埋まる
4. **前提と順序** — 各子の受け入れ条件が前提にする機能・データ・画面・API が、既にある
   (`path` で確かめた) か、依存に書いた先の子が用意するか。依存が循環せず、各子の完了
   時点でその子の条件をすべて検証できるか。先の子がマージ済みなら、実装されたコードを
   読んで前提を確かめ直す

**子ごと**

5. **属するか** — 各条件が、その子のタイトルと背景・作業内容だけで説明がつき、その子の
   変更の範囲で満たせるか。親の目的では説明がつくが、その子の目的では説明がつかない条件は
   兄弟の条件か、新しい子の条件
6. **実装で止まらないか** — `issue-implement` が止まる理由が無いか。1 件ごとに、落ちる
   テストの前提・操作・期待が書けるか。「適切に」「必要に応じて」「など」のように実装者に
   振る舞いを選ばせる語が無いか。別の振る舞いを 1 件に束ねていないか

### 3. 直し先を決める

指摘ごとに、穴を誰が埋めるかを決める。子 1 つを見れば「その子に足す」が常に最短に
見えるので、上から順に当てはめ、当てはまった最初のものを直し先にする。

1. **兄弟** — 穴を埋める振る舞いが、兄弟の目的で説明がつくか、兄弟のスコープ外・受け入れ
   条件に既に行き先として書かれている。その兄弟が着手済みなら、ここには当てはめない
2. **分け直し** — 穴を埋めると、子の目的が変わるか、2 つの子の範囲を跨ぐ。子を足す・
   統合する・境界を引き直すことになる。P1 が 5 件を超えた子もここ
3. **親** — 親の受け入れ条件そのものが欠けているか、矛盾している。分解では直せず、
   設計に戻る
4. **その子** — 上のどれでもない。その子の目的と変更の範囲の中で埋まる

「その子」に当てはめたときは、根拠に「兄弟 #n の範囲ではない」理由を添える。添えられ
ないなら、当てはめる直し先を取り違えている。

### 4. 報告する

報告は 1 回にまとめる。

- **判定** — 子ごとに 1 行。`#n 着手可` か `#n 要修正 (P1 N 件)`。起票前なら仮番号で
- **直し先ごとの指摘** — 直し先 (その子ごと・兄弟の移動・分け直し・親) でまとめ、
  出力規約の形で並べる。受け取り手は直し先のまとまりをそのまま入力にする
- **次の一手** — 1 行。指摘を受け取る工程と、直した後にこのレビューをセットでやり直すこと

起票済みのセットなら「チケットにコメントする」で親に残す。折りたたみが使えない置き場所
(能力層が示す) では根拠を省かず、直し先ごとのまとまりを保ったまま記号で区切る。

## 指摘の受け取り手

| 直し先 | 受け取る工程 | 何をするか |
| --- | --- | --- |
| 兄弟・分け直し | `issue-plan` の「レビュー指摘を受けたら」 | 条件を子の間で移す。子を足す・統合する |
| その子 | 一式の指摘と一緒なら `issue-plan`、その子だけなら `issue-design` の「レビュー指摘を受けたら」 | その子の本文を直す。既存コードに当てて仕様を詰め直す穴は `issue-design` |
| 親 | `issue-design` の「レビュー指摘を受けたら」 | 親の本文を直し、分解をやり直す |

親を持たないチケットの指摘は、直し先がすべて「その子」になり、`issue-design` が受け取る。

直した後は、このレビューをセット全体でやり直す。1 つの子を直すと、兄弟との境界が動く。
同じ子の組の境界について、2 回続けて P1 が出たら、個別の指摘を並べるのをやめ、分け直しの
案を最大 3 案、人間に示す。指摘を足して直すことを繰り返すと、境界は直らずに片方の子が
膨らむ。

## やらないこと

- チケットの起票・本文の書き換え (受け取り手の工程の領分)
- 子チケット 1 つだけを読んだレビュー (親があるとき)
- 直し先の無い指摘、兄弟の範囲かどうかを確かめずに「その子」を直し先にした指摘
- 着手済みの子を直し先にすること
- 実装の細部 (クラス名・関数名・画面文言) の指摘
- 実装の着手の承認の代行 (GitHub の `ai:go` の付与)
- チケットの状態の変更
