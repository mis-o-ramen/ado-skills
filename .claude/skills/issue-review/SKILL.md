# チケットレビュー — 着手前のチケットをセットで見る

実装に着手する前のチケットを、親と兄弟の子チケットとまとめて 1 つのセットとして読み、
直し先の付いた指摘を返すまでの手順。GitHub でも Azure DevOps でも同じ手順で動く。
チケットレビューは開発ループの段ではなく支援工程で、チケットを直さない。指摘は直し先に
応じて設計の工程 (`issue-design`) か分解の工程 (`issue-plan`) が受け取る。

子チケット 1 つだけを読むレビューは、足りないものをすべてその子に足す方向にしか指摘
できない。兄弟に回した振る舞いも「抜け」に見え、直すたびに子の範囲が兄弟に食い込む。
この工程が単位をセットにするのはそのため。

セットは**親の成果から読む**。受け入れ条件の範囲の中だけを読むレビューは、条件どうしの
矛盾と抜けしか指摘できず、指摘を直すたびに条件が細かくなる。条件が親の目的に役立って
いるかを問わないまま細かくなると、条件を満たすことが目的に置き換わる。だから、足りない
ものと同じ重さで、目的から外れたもの・詰めすぎたものも指摘する。

子チケットには 2 つの状態がある。分解の工程が起票した**骨組み** (成果はあるが受け入れ条件が
無い) と、設計の工程が着手の直前に受け入れ条件を書いた**詳細化済み**。骨組みの子に受け入れ
条件が無いことは指摘しない。

## この工程の入口

入口条件: **実装に着手していないチケットがあり、着手の前に確かめたい** (ループの定義は
`dev-loop` スキル)。次のどれかで呼ばれる。

- 設計の工程が、親チケット・親を持たないチケット・詳細化した子の本文の承認を求める前
  (「Subagent でかける」で必ず通す)
- 分解の工程が、子チケットの下書き一式の承認を求める前と、指摘を反映した後 (同じく必ず通す)
- 先の子チケットがマージされた後。残りの子の前提が、実装されたコードとずれていないか
- 人間が、直接直したチケットを確かめたいとき

条件が違う依頼は該当する工程に渡す。

- PR のレビュー → `pr-review`
- 指摘を受けてチケットを直す → 直し先ごとの受け取り手は下の「指摘の受け取り手」の表
- 着手済みのチケット (紐づく PR がある) の受け入れ条件の不足 → 実装の工程が止まって
  返した不足として `issue-design` に渡す

## 能力層

基盤ごとに違う操作は、この本文に「子チケットを一覧する」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

**チケット**は GitHub の Issue、Azure DevOps の作業アイテム。**親チケット**は GitHub の
Epic、Azure DevOps のフィーチャー。**受け入れ条件**は Azure DevOps では型ごとのフィールド
(受け入れ基準など) に入る。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 起動 | 設計・分解の工程が Subagent で呼ぶ。依頼者が呼ぶ | 設計・分解のワークフローが Subagent で呼ぶ。親か子に `ai:check` が付いたとき、子がクローズされたとき |
| 対象 | 起票前の下書きか、起票済みのチケット | Subagent では起票前の下書きか対象のチケット。`ai:check` とクローズでは起票済みのチケット |
| 報告の置き場所 | Subagent なら呼んだ工程に返すだけ (残し方は呼んだ工程が決める)。起票済みのセットを依頼者が別のセッションでレビューさせたなら「チケットにコメントする」で親に残し、会話でも返す。先頭行は手順 5 の報告の行 | Subagent なら呼んだ工程に返すだけ。それ以外は「チケットにコメントする」で親 (親が無ければそのチケット) に 1 コメント。ワークフローが指定する行を先頭に置く |
| 着手可の判定 | Subagent か別のセッションでレビューしたときだけ出す | 出す |

着手可の判定を出せるのは、チケットを書いた側の判断を持たずに読んだレビューだけ。チケットを
書いたのと同じ会話で、書いた本人がかけたレビューは自己レビューになる。書いたときの判断を
前提に読むので、その判断の外にある穴が見えない。下書きを整えるのには使えるが、判定は
`#n 着手可` の代わりに `#n 自己レビューで P1 なし` と書く。自己レビューの報告は親に残さない。
残すと、次のレビューが前回の報告として読み、収束の条件の回数にも入る。

「Subagent でかける」の依頼文で呼ばれた Subagent は、書いた側の判断を受け取っていないので、
自己レビューではない。依頼文に書いた側の判断 (なぜそう書いたか、意図的に外したもの) が
混ざっていたら、それは依頼文の形から外れている。混ざった判断は、手順 3 で読む記録として
だけ扱う。

チケットの状態 (GitHub の状態ラベル `ai:*`、Azure DevOps の `System.State`) は動かさない。
GitHub Actions では、報告を読んだワークフローがラベルを付け替える。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の優先度と上限は次のとおり。

| 優先度 | 基準 |
| --- | --- |
| P1 | このまま進めると実装の工程が止まるか、推測で埋まるか、親の目的から外れたものが作られる。子どうしの重複・矛盾、どの子にも無い親の成果、親の成果で説明のつかない子の成果・条件、その子に属さない成果・条件、前提の出どころが無い成果・条件 |
| P2 | 実装は一意に決まるが、読み手を迷わせるか、詰めすぎている。表記の揺れ、別々の操作を束ねてはいないが分けたほうが読みやすい条件 (同じ前提・同じ操作から出る結果を並べた条件は除く)、既存に揃えれば決まる振る舞いを書いた条件 |

チケットはそれ自体では何も壊さないので、P0 は使わない。迷ったら低い方に倒す。

P1 には、次のどれかの**証拠**を 1 つ添える。添えられない指摘は、どれだけ重く見えても P2
にする。「推測で埋まる」かどうかは読み手ごとに揺れるので、証拠の無い P1 はレビューの
たびに入れ替わり、直しても収束しない。

- **2 通りの実装** — その条件を満たす実装が 2 通りあり、外から見える振る舞いが違う。
  その 2 通りを 1 句ずつ書く
- **書けないテスト** — 条件から、落ちるテストの前提・操作・期待のどれが書けないか
- **表の欠け** — 手順 2 の被覆表・追跡表・境界表で欠けているか重なっている行。行の中身を書く
- **出どころの無い前提** — 条件が前提にする機能・データ・画面・API のうち、既にある
  (`path`) とも、どの子が用意するとも言えないもの

- P1 は、子 1 つあたり **5 件まで**。超える子は、指摘を足して直す段階に無い。その子の
  個別の指摘を並べず、「分け直し」を直し先にした 1 件にまとめ、超えた理由 (境界が
  どこで崩れているか) を 1 行で書く
- P2 はセット全体で **3 件まで**。溢れた分は `- その他 P2 N 件` の 1 行だけで示す
- 指摘は 1 件 1 行、`[P1] 観点 — 指摘 — 証拠 — 直し先 — 根拠 — 分類` の形にする。根拠は
  `path:line`、チケットの成果か条件の番号、親の成果番号のどれか。分類は手順 3 の新規・修正で
  生じた・再指摘のどれか。P2 は証拠を省いてよい

## 手順

### 1. セットを集める

レビューする単位は、親チケットと、その親のすべての子チケット。

1. 起点のチケットを「チケットを読む」でコメントまで読む
2. 「親チケットを読む」で親を読む。親があれば「子チケットを一覧する」で兄弟をすべて集め、
   それぞれ「チケットを読む」で読む。起票前の下書きなら、分解の工程が示した下書き一式を
   そのまま使う
3. 各子について、骨組みか詳細化済みか (受け入れ条件があるか)、着手済みか (紐づく PR が
   あるか、マージ済みか) を控える。着手済みの子は読むが、直し先にしない (手順 4)
4. 親のコメントに、実装の工程が残した先頭行が `成果との差` のコメントがあれば控える。
   マージ済みの子が条件を満たしても届かなかった成果で、観点 1 では、その差を担う子が
   あるかを確かめる。無ければ漏れ

**記録は手順 3 で読む。** 次のものは、読み込まれても手順 2 の判断の根拠にしない。

- 前回までのチケットレビューの報告 (被覆表・追跡表・境界表を含む)
- 指摘への対応の記録 (分解・設計の工程が親に残した、先頭行が `チケットレビューへの対応` のコメント)
- 設計の検討記録 (設計メモ、報告のコメントの折りたたみ)

前回の報告を先に読むと、前回の指摘が直ったかを確かめる作業になり、前回見なかった箇所を
見ない。記録を先に読むと、書いた側の判断の中で読むことになる。どちらも、書いた側や前回の
レビュアーと同じ見落としを繰り返す。チケットの本文にあるスコープ外・設計判断は本文なので、
手順 2 で読む。

親があるのに兄弟の一部しか手に入らないときは、レビューを始めずに、足りない子を依頼者に
求める。兄弟が欠けたセットでは、手順 2 の境界を判定できない。

リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
受け入れ条件が前提にするコードは、ファイルを開いて確かめる。

### 2. 観点ごとに確かめる

セット全体の観点を先に見て、子ごとの観点は後に見る。子ごとに見てから全体を見ると、
個々の子の「足りない」がすべてその子への追加として指摘される。

**親だけ** — 子がまだ無い親チケット (設計の工程が起票する前の下書き) は、観点 1〜6 の
代わりに次だけを見る。被覆表・追跡表・境界表は作らない。

- 成果 1 件ごとに、背景・目的で説明がつくか。説明のつかない成果は削る指摘
- 成果どうしが重なっていないか。重なると、分解で同じ振る舞いを 2 つの子が担う
- 成果に実装の層 (画面・API・データ) や操作の手順が混ざっていないか。混ざると、分解が
  層で切る
- 成果が 1 つで、変わる箇所も 1 つにまとまるなら、親にする理由が無い。1 チケットに戻す指摘

P1 の証拠は、該当する成果の番号と、上のどれに当たるかを 1 句で書く。直し先はすべて「親」。

**セット全体**

最初に、親の背景・目的と成果だけを読み、何が達成されたら終わりかを掴む。子の本文はその
後に読む。子から読むと、子に書かれたことの範囲の中で穴を探すことになる。

観点 1〜3 は、指摘を探す前に表を作る。表は誰が作っても同じ中身になるので、レビューの
たびに指摘が入れ替わる範囲を、観点 4〜6 に絞れる。表は報告の折りたたみに載せる。

- **被覆表** — 親の成果 1 件 1 行。`親の成果番号 — それを担う子の成果` (無ければ `なし`、
  2 つ以上なら全部)
- **追跡表** — 子の成果 1 件 1 行。`#n の成果 — それが担う親の成果番号` (無ければ `なし`)。
  詳細化済みの子と親を持たないチケットは、受け入れ条件 1 件 1 行も足す。成果の見出しが
  無い子 (この形より前に起票された子) は、受け入れ条件を成果の代わりに使う。
  `#n の条件番号 — それが担う成果` (無ければ `なし`)
- **境界表** — 子のスコープ外 1 行につき 1 行。`#n のスコープ外の項目 — 行き先の子の
  成果か条件` (無ければ `なし`)

1. **被覆** — 親の成果が、どれか 1 つの子の成果に落ちているか。どの子にも無い親の成果は
   漏れ、2 つ以上の子にある成果は重複。親の成果が画面で観測されるなら、その画面を作ることが
   どれかの子の作業内容にあるかも見る。サーバ側だけが子に落ち、画面がどの子にも無いのは
   漏れ。子を層 (サーバ・画面) で切っているなら、ここは必ず確かめる
2. **目的との整合** — 追跡表で `なし` の行。親の成果で説明のつかない子の成果、成果で説明の
   つかない受け入れ条件は、目的から外れている。直し方は削るか、親に成果が足りないなら親に
   戻すかで、関係の薄い成果に結びつけて残さない
3. **境界** — 各子のスコープ外に書かれた項目が、その行き先の兄弟の成果か受け入れ条件として
   実在するか。逆に、子の成果・受け入れ条件が、別の子のスコープ外に「この子でやる」と
   書かれた範囲を越えていないか
4. **前提と順序** — 各子の成果・受け入れ条件が前提にする機能・データ・画面・API が、既に
   ある (`path` で確かめた) か、依存に書いた先の子が用意するか。依存が循環しないか。
   先の子がマージ済みなら、実装されたコードを読んで前提を確かめ直す。詳細化済みの子が
   まだ入っていない兄弟に依存するなら、その兄弟が無い状態の振る舞いが受け入れ条件で
   決まっているか

**子ごと**

5. **属するか** — 各成果・条件が、その子のタイトルと背景・成果・作業内容だけで説明がつき、
   その子の変更の範囲で満たせるか。親の目的では説明がつくが、その子の目的では説明がつかない
   ものは兄弟のものか、新しい子のもの

観点 6 は、詳細化済みの子と、親を持たないチケットにだけ当てる。

6. **実装で止まらないか** — `issue-implement` が止まる理由が無いか。1 件ごとに、落ちる
   テストの前提・操作・期待が書けるか。「適切に」「必要に応じて」「など」のように実装者に
   振る舞いを選ばせる語が無いか。1 件が次の書き方と 1 件に書く範囲の規則に収まっているか
   (`issue-design` の手順 6 と同じ文。この節だけで判定してよい)。前提・操作・結果が読めず
   テストが書けない条件と、どこで観測するか (画面・API・ログ・データ) が文から読めない条件は
   P1。後者は、実装が層を選んで残りを兄弟に回す。書き方が型の例と違うだけで、前提・操作・
   観測点・結果が読める条件は指摘しない (P2 にもしない)
   <!-- ac-form:begin -->
   - 1 件から、前提 (どの状態で)・操作 (何をすると)・観測点 (どこで — 画面・API・ログ・
     データ)・結果 (何が起きるか) が読めるように書く。語順と言い回しは問わない。前提の無い
     条件は前提を、状態だけを述べる条件と「〜は変わらない」の条件は操作を省いてよい
   - 型の例は `［前提］とき、［操作］と、［観測点］は［結果］`。例は書きやすくするための型で、
     合否の基準ではない
   - 同じ前提・同じ操作から一緒に出る結果は、1 件に並べて書いてよい。テストは 1 本で、
     並べた結果がすべて見えれば合格になる
   - 型に入れると意味が変わる条件 (性能・セキュリティなどの非機能、いつも成り立つべき
     不変条件、複数の操作をまたぐ一連の流れ) は、型に収めず平文で書く。そのときも、どこで
     何を確かめれば満たされたと言えるかを文から読めるようにする
   - バグの再現手順は混ぜない (別の見出しに書く)。直った後の振る舞いを書く
   <!-- ac-form:end -->
   <!-- ac-scope:begin -->
   - 1 件には、このチケットで変わる振る舞いを 1 つだけ、利用者 (API なら呼び出し側) から観測
     できる形で書く。別の操作が起こす振る舞いを「、」「かつ」「また」で足さない。同じ前提・同じ
     操作から一緒に出る結果は、観測点が画面とデータに分かれていても並べてよい。束ねた条件は合否を
     1 件単位で判定できず、一部だけ満たした実装が通るか落ちるかが決まらない
   - どこで観測するか (画面・API・ログ・データ) を文から読めるようにする。
     「〜を登録できる」だけでは、画面から登録できるのか API で登録できるのかが決まらず、実装は
     作りやすい層だけを作って、残りを別のチケットの管轄と読む
   - 受け入れ条件はテストケースの一覧ではない。同じ操作に同じ期待を持つ入力の違い (境界値、
     不正値の種類) は値ごとに並べず、振る舞いとして 1 件に書く。どの値で確かめるかは実装の
     工程が決める。書く「上限を超える件数を渡すと、API は上限を示すエラーを返し、1 件も保存
     しない」。書かない「101 件で〜」「1000 件で〜」「負の数で〜」を
     別々の条件にする
   - 既存の振る舞いに揃えれば一通りに決まる振る舞いは条件にしない。条件にするのは、この
     チケットで決める振る舞いだけ。揃える先は検討記録に `path:line` で残す
   <!-- ac-scope:end -->

観点 6 の指摘は「どの条件の、何 (前提・操作・観測点・結果) が読めない」の形で書き、文を足す
修正案を添えない。足す案を出すと、直す側は元の文に節を足し、往復のたびに読めない文に
なる。

「境界・異常系の条件が無い」という指摘は、その振る舞いが既存に揃えれば一通りに決まるなら
出さない。設計の検討記録に揃える先があるかは手順 3 で照らす。

### 3. 記録に照らす

手順 2 の指摘が出そろってから、手順 1 で後回しにした記録を読む。起票済みのセットなら、
親のコメントに残った前回までのレビューの報告と、指摘への対応の記録を読む。設計の検討記録は、
チケットのコメントにあればそこで、依頼者がファイルを示したならそのファイルで読む。
指摘ごとに、次のどれかに分ける。

- **未対応** — 前回の報告で直し先が「その子 (詳細化済み)」か「親」だった指摘と同じ穴で、
  そのチケットの本文が前回の報告より後に書き換わっていない。分解の工程はこの 2 つを直さない
  ので、分解の反映の後に回ったレビューでも同じ指摘が出る。指摘の行は出さず、判定を
  `#n 要修正 (前回の指摘が未対応)` にする。P1 の件数にも打ち切りの回数にも数えない
- **再指摘** — 前回の指摘か検討記録に、同じ穴への結論と根拠がある。根拠が指すコード・条件を
  今の本文とコードで開いて確かめ、この指摘がその根拠を崩すときだけ残し、崩す理由を 1 句
  添える。崩さない指摘は報告から外す。根拠の箇所がその後に書き換わっていれば、根拠は
  今の本文で確かめ直すことになるので、書き換えで崩れた根拠はここで拾える
- **修正で生じた** — 前回の報告より後の対応の記録に、変わった子・移した成果として挙がった
  箇所から出た。そのまま残す。対応の記録に挙がっていない書き換え (人間が本文を直接直した
  など) は、判定の材料が無いので次の新規に倒す
- **新規** — 上のどれでもない。そのまま残す

記録に結論が書いてあることは、それが正しいことの証拠にならない。根拠を開かずに外さない。
逆に、根拠を崩す理由を言えない再指摘は、書いた側が一度答えた穴を、前と同じ材料で
もう一度問うことになる。直す側は同じ答えを返すしかなく、往復が収束しない。

### 4. 直し先を決める

指摘ごとに、穴を誰が埋めるかを決める。子 1 つを見れば「その子に足す」が常に最短に
見えるので、上から順に当てはめ、当てはまった最初のものを直し先にする。

1. **兄弟** — 穴を埋める振る舞いが、兄弟の目的で説明がつくか、兄弟のスコープ外・受け入れ
   条件に既に行き先として書かれている。その兄弟が着手済みなら、ここには当てはめない
2. **分け直し** — 穴を埋めると、子の目的が変わるか、2 つの子の範囲を跨ぐ。子を足す・
   統合する・境界を引き直すことになる。P1 が 5 件を超えた子もここ
3. **親** — 親の成果そのものが欠けているか、矛盾している。分解では直せず、
   設計に戻る
4. **その子** — 上のどれでもない。その子の目的と変更の範囲の中で埋まる

「その子」に当てはめたときは、根拠に「兄弟 #n の範囲ではない」理由を添える。添えられ
ないなら、当てはめる直し先を取り違えている。

目的との整合 (観点 2) の指摘は、削る指摘として、その成果・条件を持つ子 (親に成果が足りない
なら親) を直し先にする。

### 5. 報告する

報告は 1 回にまとめる。親に残す報告の先頭行は `チケットレビュー ラウンド N · P1 M 件`
(GitHub Actions ではワークフローが指定する行)。N は親に残った前回までの報告の最大の
ラウンド + 1 (初回は 1)、M は手順 3 を通って報告に残した P1 の件数。下の「収束の条件」で
打ち切ったなら、行の末尾に ` · 打ち切り` を足す。この行が、次のレビューが前回の報告と
回数を数える目印になる。

- **判定** — 子ごとに 1 行。`#n 着手可` (骨組みの子なら `#n 詳細化可`、親だけなら
  `親 分解可`)、`#n 要修正 (P1 N 件)`、`#n 要修正 (前回の指摘が未対応)` のどれか。起票前なら
  仮番号で。自己レビューなら「実行文脈による違い」のとおり `#n 自己レビューで P1 なし`
- **直し先ごとの指摘** — 直し先 (その子ごと・兄弟の移動・分け直し・親) でまとめ、
  出力規約の形で並べる。受け取り手は直し先のまとまりをそのまま入力にする
- **外した再指摘** — 手順 3 で外した件数を 1 行。外した指摘ごとに、引いた記録と、根拠を
  開いて確かめたことを折りたたみに 1 行で残す。次のレビューと、記録を書いた側が引く
- **被覆表・追跡表・境界表** — 折りたたみに
- **次の一手** — 1 行。指摘を受け取る工程と、直した後にこのレビューをセットでやり直すこと。
  下の「収束の条件」で打ち切ったなら、人間が決めること

起票済みのセットなら「チケットにコメントする」で親に残す。折りたたみが使えない置き場所
(能力層が示す) では根拠を省かず、直し先ごとのまとまりを保ったまま記号で区切る。

## Subagent でかける

設計・分解の工程が、承認を求める前にこのレビューを自分で回すときの手順。呼ぶ側の工程は
この節に従う。Subagent は、実行環境が持つ Subagent を起動するツール (Claude Code の Agent /
Task、GitHub Copilot の runSubagent など) で起動する。

**依頼文は次の形で書く。** 書いた側が、なぜそう書いたか、何を意図的に外したかを書き足さ
ない。書き足すと、Subagent は書いた側の判断の中で読み、自己レビューと同じ見落としをする。
実行文脈が足すよう指示した場所や制約は「前提」の行に書く。

```
issue-review の手順でチケットをレビューする。手順は <スキルの場所> を全文読む。
前提: <実行文脈 (チャット / GitHub Actions)、基盤と能力層のスキルの場所、ほかに読むスキルの場所>
観点: <「親だけ」(子がまだ無い親の下書き) か「通常」>
対象: <下書きのファイルのパス、またはチケット番号>
親: <親の下書きのパスかチケット番号。無ければ「なし」>
兄弟: <兄弟のチケット番号か下書きのパス。無ければ「なし」>
手順 3 で読む記録: <検討記録・前回の報告・対応の記録の場所。無ければ「なし」>
報告は手順 5 の形で返すだけにし、チケットには書かない。チケットもファイルも変更しない。
```

1. 新しい Subagent を起動して、上の依頼文でレビューさせる
2. 返った報告を、呼んだ工程の「レビュー指摘を受けたら」で反映する。P1 だけを直す。P2 は
   直さずに、承認を求めるときに 1 件 1 行で添える
3. P1 を直したら、**新しい** Subagent でもう 1 周かける。前の Subagent に続けて頼まない
   (直した理由を聞いた後の読み手は、書いた側と同じ判断の中で読む)。前回の報告と対応の記録を
   「手順 3 で読む記録」に足す
4. 周回は最大 2 周。2 周目で P1 が 0 件になるか、2 周目が終わったら止める。P1 が残ったら、
   それ以上直さずに、残った P1 を承認の求めに添えて人間に返す。周回を重ねると、条件を
   細かくする方向にしか進まない

途中の周回の報告は親に残さず、収束の条件の回数にも数えない。最後の周回の報告を親に残すか
どうかは、呼ぶ側の工程 (GitHub Actions ではワークフロー) が決める。親に残した最後の報告は、
収束の条件で 1 回の報告として数える。

## 指摘の受け取り手

| 直し先 | 受け取る工程 | 何をするか |
| --- | --- | --- |
| 兄弟・分け直し | `issue-plan` の「レビュー指摘を受けたら」 | 成果を子の間で移す。子を足す・統合する |
| その子 (骨組み) | `issue-plan` の「レビュー指摘を受けたら」 | その子の骨組みを直す |
| その子 (詳細化済み) | `issue-design` の「レビュー指摘を受けたら」 | その子の受け入れ条件を直す |
| 親 | `issue-design` の「レビュー指摘を受けたら」 | 親の成果を直し、分解をやり直す |

親を持たないチケットの指摘は、直し先がすべて「その子」になり、`issue-design` が受け取る。

直した後は、このレビューをセット全体でやり直す。1 つの子を直すと、兄弟との境界が動く。
同じ子の組の境界について、2 回続けて P1 が出たら、個別の指摘を並べるのをやめ、分け直しの
案を最大 3 案、人間に示す。指摘を足して直すことを繰り返すと、境界は直らずに片方の子が
膨らむ。

この 2 回と、下の「収束の条件」の打ち切りの 3 回は、数える単位が違う。分け直しの案は、
同じ子の組の境界ごとに前回の報告と比べて数える。打ち切りは、セット全体で P1 が出た報告が
何回続くかを数える。分け直しの案を示しても、打ち切りの回数は数え直さない。

## 収束の条件

レビューの目的は、実装の工程が止まらずに進めるセットにすることで、どのレビュアーが
読んでも指摘が出ないセットにすることではない。レビューは読む箇所を毎回変えるので、読み手を
変えれば指摘は出続ける。終わりは次の 2 つで決める。

- **着手可** — チケットを書いた会話・実行とは別のレビューで、手順 3 を通って報告に残った
  P1 (新規・修正で生じた・根拠を崩す再指摘) が 0 件になった。外した再指摘と P2 は数えない。
  骨組みの子では、着手可ではなく詳細化可と書く
- **打ち切り** — 直してもそのたびに P1 が出る状態が 3 回続いた。指摘を足して直す段階に
  無いので、個別の指摘を直し先に返すのをやめ、残った P1 を並べて、人間に次から選んでもらう。
  - A: このまま進める (残った穴は、詳細化か実装の工程が止まって返す)
  - B: 分け直す (`issue-plan` に、残った P1 が集まる境界を示して渡す)
  - C: 親に戻る (P1 が親の成果の欠けに集まるとき。`issue-design` に渡す)

打ち切りの回数は、親に残った報告 (先頭行が手順 5 の報告の行のもの) を、今回を含めて新しい
順にたどり、P1 が 1 件以上の報告が何回続くかで数える。次のものは数えない。

- 末尾が `打ち切り` の報告と、それより前の報告。人間が選んだ後は、数え直す
- 前の報告との間に、指摘への対応の記録が無い報告 (子のクローズで走ったなど、直して
  いない一式のレビュー)。ただし、前の報告が無い最初の報告は数える

A で着手してよいのは、実装の工程が、受け入れ条件から実装が一意に決まらなければ推測で
埋めずに止まり、足りない条件をチケットに返すからだ。着手前に取り切れなかった穴の損失は、
実装が 1 回止まることまでに収まる。

## やらないこと

- チケットの起票・本文の書き換え (受け取り手の工程の領分)
- Subagent として呼ばれたときの、チケットへのコメント
- 子チケット 1 つだけを読んだレビュー (親があるとき)
- 直し先の無い指摘、兄弟の範囲かどうかを確かめずに「その子」を直し先にした指摘
- 証拠の無い P1
- 骨組みの子に受け入れ条件が無いことの指摘
- 書き方が型の例と違うだけで、前提・操作・観測点・結果が読める条件への指摘
- 親の成果に照らさずに、受け入れ条件の範囲の中だけで抜けを探すこと
- 記録に結論があることだけを理由に、根拠を開かずに指摘を外すこと
- 着手済みの子を直し先にすること
- 実装の細部 (クラス名・関数名・画面文言) の指摘
- 実装の着手の承認の代行 (GitHub の `ai:go` の付与)
- チケットの状態の変更
